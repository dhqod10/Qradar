## 3. 서비스 구조 (심사역에게 설명할 한 문단)

Qradar는 카페 **픽업 주문** 앱이다. 배달이 없고, 이용자가 앱에서 매장과 메뉴를 고른 뒤
결제하면 매장이 제조하고 이용자가 직접 찾아간다. 판매 상품은 **주문 후 즉시 제조되는
식음료**이며, 이 성격이 환불 정책의 근거(전자상거래법 제17조 제2항)가 된다.

주문 상태는 `paid → accepted → making → ready → completed` 로 흐르고,
중간에 `cancelled`(조리 전 취소·매장 거절) 또는 `refunded`(접수 후 환불)로 빠진다.

## 4. 결제 처리 흐름 (기술 검토 항목)

결제 대행사는 **토스페이먼츠 주식회사** 한 곳이다.

1. 앱이 토스 결제위젯을 띄우고 이용자가 결제한다.
2. 토스가 돌려준 `paymentKey` 를 **서버(Cloud Functions)** 가 받는다.
3. 서버가 장바구니를 다시 계산해 **금액을 재검증**한 뒤 토스 승인(confirm)을 호출한다.
4. 승인 응답이 통과해야 주문 문서가 생성된다.

심사에서 강조할 점 두 가지:

- **금액 권위가 서버에 있다.** 클라이언트가 보낸 금액을 그대로 믿지 않고, 서버가
  메뉴·옵션 가격을 다시 조회해 계산한 값으로 승인을 건다. 금액 조작이 불가능하다.
- **카드정보를 보관하지 않는다.** 카드번호·CVC·계좌번호는 앱과 서버 어디에도 저장되지
  않고 토스페이먼츠가 처리한다. 개인정보처리방침에도 같은 내용이 적혀 있다.

주문 생성은 클라이언트에서 직접 할 수 없도록 Firestore 규칙에서 막혀 있고
(`orders.create: if false`), Cloud Function만 Admin SDK로 생성한다.

## 5. 취소·환불 처리 (정책 ↔ 구현 대응)

| 시점 | 이용자 동작 | 처리 |
|---|---|---|
| 결제 완료·접수 전 | 앱에서 직접 취소 | 전액 환불 (`cancelTossPayment`) |
| 매장 거절 | 신청 불필요, 자동 취소 | 전액 환불 (`cancelTossPayment`) |
| 접수 이후 | 환불 요청 → 매장 승인 | 전액 환불 (`processRefund`) |

- 환불은 **최초 결제수단으로만** 처리한다. 현금·타인 계좌 환불 없음.
- 당사 처리 기한 **3영업일 이내**, 이후 카드사 반영은 3~7영업일.
- 환불 수수료는 이용자에게 청구하지 않는다.
- 적립 Qoin은 환불 시 자동 회수되고, 사용한 Qoin은 반환된다.
- 분쟁 조정 기관(소비자분쟁조정위원회·전자거래분쟁조정위원회·공정거래위원회)이
  정책에 명시돼 있다.

## 7. 제출 전에 반드시 정리할 것 — 심사에서 걸릴 수 있는 지점

### 7-1. 결제수단 표기가 실제와 다를 수 있다 (가장 큰 리스크)

랜딩과 환불 정책에는 결제수단이 **"신용·체크카드, 간편결제(카카오페이)"** 두 가지로만
적혀 있다. 그런데 앱에서 결제수단 선택 UI를 제거했기 때문에, 이용자에게 실제로 보이는
수단은 **토스 개발자센터에 켜 둔 설정이 그대로 결정**한다. 켜 둔 수단이 두 가지보다
많으면 "정책에 없는 수단으로 결제된다"가 되어 지적 대상이다.

→ **토스 개발자센터에서 활성화된 결제수단 목록을 확인하고**, 둘 중 하나를 하라.
  - 콘솔에서 카드·카카오페이만 남기거나,
  - 켜 둔 수단 전부를 `refund.html` 제3조 표와 `index.html` 결제수단 안내에 추가하거나.

### 7-2. 환불 정책의 "부분 환불" 조항과 구현이 다르다

`refund.html` 제4조는 일부 상품만 품절·하자일 때 **부분 환불**한다고 약속하는데,
현재 구현(`processRefund`)은 **주문 금액 전액 환불만** 가능하다.

실무상으로는 전액 환불 후 재주문으로 처리할 수 있어 소비자에게 불리하지 않지만,
심사에서 "부분 환불 어떻게 처리하냐"를 물으면 설명이 필요하다.
→ 수동(고객센터 경유) 처리라고 답하거나, 조항 문구를 실제 운영에 맞춰 다듬는다.

### 7-3. 토스 클라이언트 키가 아직 테스트 키다

현재 `env.json` 의 `TOSS_CLIENT_KEY` 는 `test_gck_docs_…` 로 시작하는 **토스 공개 문서용
데모 키**다. 심사 통과 후 라이브 키로 교체해야 하며, 교체 전까지 실결제가 되지 않는다.
(심사 단계에서는 문제되지 않지만, 통과 직후 교체가 런칭 체크리스트의 첫 항목이다.)

### 7-4. 앱이 아직 스토어에 없다

첫 출시 전이라 심사역이 앱을 내려받아 볼 수 없다. 스토어 링크는 PG 심사 필수 항목이
아니므로, **앱 화면 캡처 + 테스트 계정**으로 갈음한다.

⚠️ **테스트 계정 ID/PW 를 랜딩 페이지에 넣으면 안 된다.** 랜딩은 공개 URL이라
운영 Firebase에 누구나 접속할 수 있게 된다. 심사 서류에 **별도로** 적어 제출한다.

### 7-5. 구조 표기 — 보류 중인 판단

푸터가 **"통신판매중개자가 아닌 통신판매업자"** 라고 선언하는데, 실제로는 매장이
가격과 메뉴를 직접 등록하는 중개형에 가까운 구조다. 심사에서 책임 주체를 캐물으면
설명이 필요하다. 고객센터 번호가 개인 휴대폰(010)인 점도 함께 지적될 수 있다.

둘 다 **N4(점주 정산 — Qoin 할인 부담 주체) 결정과 묶여 있어** 아직 확정하지
않은 사항이다. 이번 심사에서 그대로 갈지, 지금 정리할지를 먼저 정해야 한다.
