# 에이전트 자동화 전략

Qradar 개발·운영에서 **사람 개입을 어디까지 줄일 수 있는가**에 대한 논의 기록.

- 작성: 2026-10-21 (Phase 3c 완결 직후)
- 상태: **논의 보류 중.** 사용자 요청 시 이 문서를 기준으로 대화를 재개한다.
- 재개 지점은 문서 끝 §7 참조.

---

## 1. 이 문서가 나온 배경

Phase 3c sub-phase 3·4 를 진행하면서, 설계·구현·검증·문서화·커밋까지의 사이클을 에이전트가 거의 자율로 돌렸다. 그 과정에서 **사람이 반드시 개입해야 했던 지점**이 구체적으로 드러났고, 이를 근거로 "어디까지 자율화가 가능한가"를 정리한 것이 이 문서다.

추측이 아니라 **실측 데이터**에 기반한다.

### 2026-10-21 하루 동안의 사람 개입 — 총 9회

| 유형 | 횟수 | 내용 |
|---|---|---|
| 결제 | 2 | 실제 PG 결제. T8 / T4·T6·T13 검증용 |
| Firestore 수정 | 3 | `fcmToken` 삭제, `prompted=false`, `laterCount=0` |
| 프로덕션 배포 | 1 | `firestore.rules` |
| **판단** | **4** | T-B17 체감 평가, 범위 결정, 비가역 결정 승인 |

## 2. 핵심 통찰 — 병목은 에이전트 구성이 아니다

그날 `architect → designer → developer → tester` 4단 파이프라인을 모두 돌렸다. 그럼에도 다음 두 건을 **파이프라인이 잡지 못했다.**

### 사례 A — T-B17 (명세가 틀린 경우)

알림 권한을 거부한 직후 앱이 OS 설정으로 자동 전환되는 동작.

```
flutter analyze   No issues found
flutter test      34 passed
tester            FAIL 0건
→ 모든 자동 검사 통과
```

사용자가 직접 눌러보고 "거슬린다"고 판정했고, 그 판단이 맞아 **결정 E-2 를 개정**했다.
자동 검증은 *명세 대비 일치*를 본다. **명세 자체가 틀렸는지는 보지 못한다.**

### 사례 B — Log 탭 (문서가 틀린 경우)

`docs/backlog.md` 에 "Log 탭 — 현재 placeholder" 로 적혀 있었으나 실제로는 구현 완료 상태였다.
에이전트가 문서를 사실로 믿고 **"Log 탭을 만들자"고 추천**했다. 사용자가 스크린샷으로 잡았다.

원인: `grep "준비 중"` 결과에 걸린 `log_page.dart` 가 **참조 0건의 죽은 파일**이었다. 실제 Log 탭은 `orders_page.dart` 를 쓴다.

### 결론

| 막힌 것 | 원인 | 에이전트를 늘리면 |
|---|---|---|
| 결제 | 외부 PG 실물 | 해결 안 됨 |
| 소셜 로그인 | 외부 인증 | 해결 안 됨 |
| Firestore 수정 | 권한 | 해결 안 됨 |
| Log 탭 오판 | 낡은 문서를 사실로 믿음 | **오히려 악화** (전파됨) |
| T-B17 | 정답이 명세에 없음 | 해결 안 됨 |

**5건 중 4건이 에이전트 구성과 무관하다.**

> 에이전트를 똑똑하게 만드는 것이 아니라, **환경을 검증 가능하게** 만들어야 한다.

## 3. 개발 단계 — 4층 구조

```
L4  인간 큐          구조적으로 자동화 불가능한 것만. 비동기로 쌓임
L3  오케스트레이터    루프 제어 · 예산 · 에스컬레이션 · 되돌리기
L2  작업 에이전트     architect / designer / developer / tester (이미 존재)
L1  진실 기반        ← 비어 있음. 투자의 90%가 여기
```

### L1 — 진실 기반 (최우선)

에이전트가 "맞다"를 **스스로 증명할 수 있는 수단**. 없으면 에이전트는 자기 가정을 확인하고 끝난다.

**① 코드가 문서를 이기게 만들기**

문서의 상태 주장 옆에 코드 경로를 명시하게 하고, CI 가 그 경로의 실체를 확인한다. placeholder 라 적었는데 실제로 구현돼 있으면 빌드 실패.
(2026-10-21 `docs/backlog.md` 정정 시 경로를 전부 명시한 것이 이 방향의 수동 버전.)

**② 결정적 테스트 환경 — Firebase Emulator Suite**

| 현재 | 필요한 것 |
|---|---|
| 실제 Firestore | 에뮬레이터 Firestore |
| 소셜 로그인 | 에뮬레이터 Auth + 테스트 계정 (토큰 직접 발급) |
| 실제 PG 결제 | 주문 시드 스크립트 (PG 우회) |
| 수동 Console 수정 | 시드 스크립트가 상태 세팅 |

**이것 하나로 그날의 사람 개입 9회 중 5회가 사라진다.**
`test_rules/` 가 이미 첫 조각이다 — Firestore 에뮬레이터로 Rules 12건을 사람 없이 검증한다. 같은 패턴을 Auth · Functions · 주문 시드로 확장하는 것.

**③ 회귀 감지 장치**

- 골든 스크린샷 — 화면의 의도치 않은 변경 감지
- 계약 테스트 — CF ↔ 클라이언트 필드명·타입 drift 감지 (현재 cross-check 표를 사람이 눈으로 대조 중)
- Rules 테스트 — 이미 있음 (`test_rules/`)

### L2 — 작업 에이전트 (보완만)

**① 적대적 검증자 분리**

현재 tester 는 developer 와 **같은 spec 을 읽는다.** spec 이 틀리면 둘 다 틀린다.

```
현재:  spec → developer → tester(같은 spec) → PASS
개선:  spec → developer → tester
                        → red-team (의도를 모른 채 결과물만 보고 깨뜨릴 방법을 찾음)
```

**② 보고를 믿지 말고 증거를 요구**

그날 developer 가 "저장소 전체 재포맷 사고를 복구했다"고 보고했고, 상위 에이전트가 **diff 를 직접 확인**해 통과시켰다. 자율 모드에서는 이 확인자가 없다.

```
보고 형식:   주장 + 증거(명령어 + 원문 출력)
오케스트레이터: 증거를 재실행해 대조. 증거 없는 주장은 반려
```

### L3 — 오케스트레이터

핵심은 **멈추는 조건**이다.

```
작업 선택 → 구현 → 자동 검증 → 실패?
                                 ├ 예 → 수정 (최대 N회)
                                 │        └ N회 초과 → L4 큐
                                 └ 아니오 → 커밋
```

| 장치 | 목적 |
|---|---|
| 수정 시도 상한 | 같은 실패를 반복하며 코드를 망가뜨리는 것 방지 |
| 되돌리기 지점 | 작업마다 브랜치. 망치면 통째로 폐기 |
| 예산 상한 | 토큰·시간 |
| 변경 범위 가드 | `dart format` 전체 재포맷 같은 사고 차단 |
| 에스컬레이션 | 막히면 **조용히 우회하지 말고** 큐에 넣고 다음 작업으로 |

마지막이 가장 중요하다. 자율 에이전트의 전형적 실패는 멈추는 것이 아니라 **막힌 것을 우회해 엉뚱한 것을 만드는 것**이다.

### L4 — 인간 큐

```
NEEDS_HUMAN.md
├ [결제]  주문 1건 필요 — owner_sales T3 검증용
├ [판단]  환불 차감 기준: 주문일 vs 환불일
├ [배포]  firestore.indexes.json 변경
└ [체감]  매출 화면 기간 전환 애니메이션 확인
```

현재는 막힐 때마다 사용자를 멈춰 세운다. 큐가 있으면 **에이전트는 다음 작업을 계속하고**, 사용자는 편할 때 몰아서 처리한다.

## 4. 운영 단계 — 개발보다 유리하다

### 왜 유리한가 — 운영에는 "정답"이 있다

개발 단계의 본질적 한계는 *무엇이 맞는지 판단할 근거가 없다*는 것이었다. 운영에는 그것이 숫자로 존재한다.

```
개발:  "이 동작이 거슬리나?"          → 사람이 눌러봐야 앎
운영:  알림 설정 진입 후 이탈률 42%    → 측정됨
       권한 허용률 11%                → 측정됨
```

**개발에서 사람이 하던 판단의 상당 부분이 운영에서는 관측 가능해진다.**

불리해지는 것은 하나뿐이다 — **실수의 대가.** 개발은 되돌리면 되지만 운영은 실제 사용자와 돈이 걸린다.
따라서 기준이 "할 수 있나"에서 **"되돌릴 수 있나"** 로 바뀐다.

### T0 — 읽기만 (완전 자율 가능, 지금도 가능)

| 업무 | 수단 |
|---|---|
| CF 에러 모니터링 | `firebase functions:log` |
| 주문 적체 감지 | `accepted` 상태 N분 초과 탐지 |
| 환불 요청 미처리 | `refundRequested` 경과 시간 |
| FCM 실패율 | 토큰 무효 / 전송 실패 비율 |
| Rules 거부 급증 | 배포 사고 신호 |
| Firestore 읽기 비용 추이 | **S5(매출 CF 집계) 전환 시점 판단 근거** |
| 크래시 / ANR | Crashlytics |
| 스토어 리뷰 수집·분류 | |

여기에 **진단과 수정안 작성까지** 포함된다.

```
에러 감지 → 원인 분석 → 에뮬레이터 재현 → 수정 코드 → 테스트 → PR 생성
→ 사람은 머지만
```

PR 생성까지는 되돌릴 것이 없다. 머지가 사람 몫이다.

### T1 — 되돌릴 수 있는 쓰기 (조건부 자율)

피처 플래그 on/off, 공지·배너 게시, 운영 설정값 조정, 캐시·인덱스 재생성.

조건: **변경 전 값 기록 + 자동 롤백 조건 + 변경 로그.**
예) 플래그를 켠 뒤 에러율이 2배가 되면 자동 복구.

### T2 — 절대 자율 금지

| 업무 | 이유 |
|---|---|
| 환불 실행 | 실제 돈. 되돌릴 수 없음 |
| 주문 상태 변경 | 고객·점주 간 분쟁 소지 |
| 계정 정지·삭제 | 되돌려도 신뢰는 돌아오지 않음 |
| 가격·정산 데이터 | 금전 |
| Rules / CF 프로덕션 배포 | 전체 영향 |
| 개인정보 접근 | 법적 |

> Qradar 는 **결제가 있는 커머스**라 T2 범위가 넓다. 콘텐츠 앱이었다면 더 공격적으로 갈 수 있다. 돈이 끼면 선을 보수적으로 긋는다.

### 운영 자율 에이전트 구성안

| 주기 | 역할 |
|---|---|
| 5분 | 상시 감시 — 임계 초과 시 알림 + **1차 진단 첨부** |
| 1일 | 일간 리포트 — 주문·매출·알림 전달률·에러·비용, 전일/전주 대비 이상치 |
| 이벤트 | 크래시 자동 분류 — 기존 이슈면 카운트, 신규면 재현 시도 → 되면 수정 PR |
| 1주 | 개선 제안 — 퍼널 이탈 지점, 느린 화면, 비정상 쿼리. 실행은 사람 결정 |

### 운영에 추가로 필요한 것

| | |
|---|---|
| 관측 지표 정의 | 무엇이 "정상"인지 숫자로. 없으면 이상 탐지 불가 |
| **읽기 전용 자격증명** | 에이전트는 프로덕션 쓰기 권한을 **갖지 않는다** |
| 변경 이력 | 누가/무엇을/언제. 롤백 근거 |

두 번째가 핵심이다. 쓰기 권한을 주지 않으면 실수해도 **구조적으로** 사고가 나지 않는다. 에이전트의 판단력에 기대지 않는 편이 낫다.

운영 단계에서도 **에뮬레이터 환경이 전제**다. 이유만 바뀐다 — 개발에서는 *사람 없이 검증하려고*, 운영에서는 *프로덕션을 건드리지 않고 재현하려고*. 없으면 에이전트가 프로덕션에서 실험하게 되는데 그것은 절대 안 된다.

## 5. 적용 우선순위

| 순위 | 할 것 | 효과 | 비용 |
|---|---|---|---|
| **1** | **Firebase Emulator Suite + 시드 스크립트** | 사람 개입 5회 → 0회. 운영 자율화의 토대도 됨 | 중 |
| 2 | NEEDS_HUMAN 큐 | 막혀도 작업 계속 | 소 |
| 3 | 증거 기반 보고 규약 | 허위 PASS 차단 | 소 |
| 4 | 문서-코드 일치 검사 | Log 탭 사고 재발 방지 | 소 |
| 5 | 골든 스크린샷 | UI 회귀 감지 | 중 |
| 6 | red-team 에이전트 | 명세 밖 결함 | 소 |

**1번이 압도적이다. 나머지를 다 합쳐도 1번 하나만 못하다.**

### 시점

```
1. 기능 완성 (매출 조회 등)
2. 에뮬레이터 환경 구축      ← 개발·운영 양쪽에 쓰임. 지금 해도 됨
3. 출시 (APNs 포함 — docs/tasks/ios_apns_setup/spec.md)
4. 관측 지표 정의 + 운영 T0 에이전트
```

## 6. 한계 — 솔직하게

이것을 다 갖춰도 **T-B17 류는 잡지 못한다.**

"거부 직후 설정 앱으로 끌려가는 것이 거슬린다"는 명세 위반이 아니라 **명세가 틀렸다는 발견**이다. 자동 검증은 명세 대비 일치를 본다.

따라서 현실적 목표는 다음과 같다.

```
❌ "사람 없이 다 한다"
✅ "사람이 판단할 것만 남기고, 그것을 비동기로 받는다"
```

2026-10-21 기준으로 환산하면:

| | 횟수 | 자동화 |
|---|---|---|
| 결제 | 2 | 에뮬레이터로 가능 |
| Console 수정 | 3 | 시드 스크립트로 가능 |
| 배포 승인 | 1 | 정책 결정 사항 |
| **판단** | **4** | **불가 — 본질** |

1번만 해도 9회 중 5회가 사라진다. 남는 판단 4회 + 배포 1회는 사람이 하는 것이 맞다.
