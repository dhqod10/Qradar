# 이력 / 감사 추적 (Audit Trail)

**무엇을 기록으로 남겨야 하는가**를 한곳에 모은 단일 진실원.

- 작성: 2026-10-22
- 계기: Qoin 적립률 설계 중 "변경 이력이 필요한가" 논의
- **새 기능을 설계할 때 §4 체크리스트를 반드시 통과시킨다.**

---

## 1. 왜 이 문서가 필요한가

이력은 **없을 때는 아쉽지 않고, 필요해진 순간에는 이미 늦은** 종류의 자산이다.

| 상황 | 이력이 없으면 |
|---|---|
| "왜 이 매장만 10%였지?" | 추적 불가 |
| 정산 분쟁 | 그 시점의 값을 증명 못 함 |
| 오입력 사고 | 언제부터 잘못됐는지 모름 |
| 되돌리기 | 이전 값을 모름 |
| 책임 소재 | 누가 바꿨는지 모름 |

Firestore 는 문서를 **덮어쓰면 이전 값이 사라진다.** 백업으로는 "언제 누가 왜" 를 복원할 수 없다.

---

## 2. 두 종류를 구분한다

설계할 때 가장 자주 혼동되는 지점이다.

| | 거래 이력 | 설정 변경 이력 |
|---|---|---|
| 대상 | 값이 **움직인 사건** | 규칙이 **바뀐 사건** |
| 예 | Qoin 540 적립 / 주문 상태 전이 | 적립률 3% → 5% |
| 빈도 | 많음 (사용자 행동마다) | 적음 (운영자 행동) |
| 보통 | 설계에 **이미 들어 있음** | **빠뜨리기 쉬움** |

> **거래 이력이 있다고 설정 변경 이력이 있는 것이 아니다.**
> Qoin 1차는 거래 원장이 완비돼 있지만 적립률 변경은 전혀 남지 않는다.

### 거래 이력의 필수 원칙 — 당시 값을 박제한다

거래 문서에 **그 시점의 정책 값을 함께 저장**한다. 참조만 하면 정책이 바뀔 때 과거 기록이 전부 틀린 값을 보여준다.

```
qoinTransactions/{id}
  amount: 540
  orderTotalPrice: 18000   ← 당시 결제액
  accrualRate: 0.03        ← 당시 적립률 (config 를 참조하지 않는다)
  balanceAfter: 1740       ← 당시 잔액
```

적립률을 5% 로 바꿔도 이 거래는 영원히 `18,000원의 3%` 다.

## 3. 현재 상태

### ✅ 이미 남고 있는 것

| 항목 | 위치 | 비고 |
|---|---|---|
| 주문 상태 전이 시각 | `orders/{id}` 의 `acceptedAt` / `makingStartedAt` / `readyAt` / `completedAt` / `cancelledAt` / `refundedAt` | 전이 시점만. 누가 했는지는 역할로 유추 |
| 결제 정보 | `orders/{id}.paymentInfo` | PG 응답 박제 (`paymentKey` / 카드사 / 승인시각) |
| 환불 정보 | `orders/{id}.refundInfo` | 금액·사유 |
| 매장 승인 메타 | `stores/{id}` 의 `submittedBy` / `submittedAt` / `approvedBy` / `approvedAt` / `rejectedReason` | **누가** 승인했는지 남는 드문 사례 |
| 브랜드 권한 연결 | `users/{uid}/roleHistory/{id}` | `claimSubmittedBrand` 가 `brandId` 설정을 값과 같은 트랜잭션에 기록 (`changedBy` = 본인 uid) |
| 주문 로그 | `users/{uid}/orderLogs/{id}` | 주문 생성 시 batch 로 함께 기록 |
| Qoin 거래 원장 | `users/{uid}/qoinTransactions/{id}` | Qoin 1차. 당시 값 박제 |
| Cloud Function 실행 | Google Cloud Logging | **30일 등 보존 기간 제한.** 영구 기록으로 믿으면 안 된다 |

### ⬜ 남겨야 하는데 없는 것

| # | 항목 | 상태 |
|---|---|---|
| **A1** | **적립률 변경 이력** (전역 / 브랜드 / 매장) | `qoin_accrual_rate_hierarchy` 의 **H7 로 포함 확정** |
| A2 | 매장 운영 정보 변경 이력 (이름·주소·영업시간 등) | 미설계. 현재 덮어쓰기만 |
| A3 | 메뉴 가격 변경 이력 | 미설계. 가격 분쟁 시 과거 가격 증명 불가 — **주문 문서에 당시 가격이 박제되는지 확인 필요** |
| A4 | 역할 변경 이력 (customer ↔ owner ↔ brand) | **부분 (2026-10-22)** — `users.brandId`(= 브랜드 권한 값) 설정만 `users/{uid}/roleHistory` 에 남는다 (`brand_authorization_hardening`). `role` 필드 자체는 여전히 덮어쓰기다. **사유**: `brandId` 를 CF 전담으로 옮긴 뒤 `role` 단독으로는 어떤 자원 권한도 주지 않는다 — 권한을 결정하는 것은 `brandId` 다 |
| A5 | admin 운영 행위 전반 (승인·반려·정지 등) | 부분적. `stores` 승인만 남고 나머지는 없음 |
| A6 | Qoin 적립 **비용 정산** | **기능 자체가 미설계.** §5 참조 |

## 4. 체크리스트 — 새 기능 설계 시 반드시 통과

architect 는 spec 작성 시, 리뷰어는 검토 시 아래를 확인한다.

1. **이 기능이 돈·권한·정책 값을 바꾸는가?**
   → 그렇다면 **설정 변경 이력이 필요하다.** 기본값은 "남긴다" 이고, 안 남기려면 사유를 spec 에 쓴다.

   > **"권한 값" 을 좁게 보지 않는다.** 역할 문자열만이 권한이 아니다. **한 필드가 어떤 자원 트리의 쓰기 권한을 결정하면 그것이 권한 값이다** — `users.brandId` 1개가 브랜드 전체와 산하 매장의 메뉴·가격 쓰기를 열었다 (`brand_authorization_hardening` §2). 그런 필드는 **클라이언트 쓰기를 닫고 CF 전담 + 이력**이 기본값이다.

2. **덮어쓰기로 사라지는 값이 있는가?**
   → 사라지면 안 되는 값인지 판단한다. Firestore 는 이전 값을 보관하지 않는다.

3. **거래/기록 문서가 정책 값을 참조만 하는가?**
   → 참조만 하면 정책 변경 시 과거 기록이 틀린다. **당시 값을 박제**한다.

4. **"누가" 가 기록되는가?**
   → 시각만 남기고 행위자를 빠뜨리기 쉽다. 운영자 행위는 `uid` 를 남긴다.

5. **일괄 처리(batch)가 있는가?**
   → 1건으로 묶어 남기되 **영향 범위(대상 수, 덮어쓰기 여부)** 를 함께 남긴다.

6. **CF 로그에 의존하고 있지 않은가?**
   → Cloud Logging 은 보존 기간이 있다. 영구 보존이 필요하면 Firestore 에 쓴다.

### 남기는 형식 (권장)

```
{컬렉션}/{id}  또는  {대상}/{id}/history/{autoId}

  changedBy    uid (운영자)
  changedAt    serverTimestamp
  scope        전역 / 브랜드 / 매장 등 적용 범위
  targetId     대상 식별자
  before       이전 값
  after        새 값
  reason       사유 (선택)
  affected     일괄 처리 시 영향받은 대상 수
```

**쓰기 주체는 Cloud Function 이 기본**이다. 클라이언트가 이력을 쓰면 위조하거나 빠뜨릴 수 있다.
(`docs/processes/data_ownership.md` §3 의 규칙 — "A 가 쓴 문서로 B 소유 문서의 집계값을 갱신해야 하면 CF" 와 같은 맥락)

## 5. 적립 비용 정산 — 미설계 영역

비용 부담 주체를 **브랜드 / 매장** 으로 확정했으므로(`backlog.md` H1), 언젠가 반드시 필요해진다.

```
현재:  Qoin 적립만 발생 — 누가 얼마를 부담하는지 집계되지 않음
필요:  매장별 적립 비용 집계 → 정산 → 청구
```

**지금 설계하지 않는다.** 세금계산서·정산 주기·분쟁 처리까지 엮여 Qoin 보다 큰 주제다.
다만 Qoin 거래 원장에 `storeId` 와 `brandId` 가 남아 있으면 나중에 집계할 수 있으므로, **원장 스키마를 정할 때 이 두 필드를 빠뜨리지 않는다.**

## 7. 데이터 유실 사고 (2026-10-26) — 이력 문서가 복구 자료가 된 사례

### 무슨 일이었나

배포 라이브 검증에서 만든 테스트 계정·브랜드를 정리하다 Firestore Console 에서
**`users` 와 `brands` 를 컬렉션 삭제**로 통째로 지웠다. 문서 10건과 그 하위
컬렉션(`orderLogs`, `qoinTransactions`, 브랜드 마스터 메뉴)이 사라졌다.
**PITR 과 예약 백업이 꺼져 있어 자동 복구가 불가능했다.**

### 이 문서가 한 일

복구를 가능하게 한 것은 **배포 직전에 적어둔 운영 기준선**이었다
(`docs/tasks/brand_authorization_hardening/spec.md` §11). 점검 카드 결과를 해석
하려고 사용자가 Console 에서 확인한 값을 그대로 적어둔 표인데, 거기에
**브랜드 계정의 uid ↔ brandId 매핑**이 남아 있었다. 그 매핑이 없었다면 어느
계정이 어느 브랜드를 가졌는지 복원할 수 없었다.

> **기록은 "나중에 필요할 때" 를 위해 남기는데, 그 "나중" 이 언제 올지는 모른다.**
> §1 의 "없을 때는 아쉽지 않고, 필요해진 순간에는 이미 늦은" 이 그대로 일어났다.

### 복구에서 결정적이었던 것

- **문서 ID 를 원본과 같게 유지**했다. `stores.brandId` 가 살아 있어서 같은 ID 로
  브랜드를 만들자 매장 ↔ 브랜드 연결이 그대로 돌아왔다.
- `users` 는 Rules(`uid() == userId`)때문에 admin 도 클라이언트에서 만들 수 없어
  Console 수동 생성이 유일한 경로였다. **권한 설계가 복구 경로를 좁힌다**는 점을
  설계 때 염두에 둘 것.
- 기존 시드로는 복구가 안 됐다. 한 batch 안에 `orderLogs`(CF 전담, `create: false`)
  쓰기가 섞여 있어 **batch 전체가 거부**됐다. 복구 도구는 **쓰려는 것만** 쓰게
  좁게 만든다.

### 복구하지 못한 것

브랜드 마스터 메뉴, `orderLogs`, `qoinTransactions`. 하위 컬렉션 내용은 어디에도
남지 않았다. `qoinTransactions` 가 사라졌다는 것은 **Qoin 거래 원장이 통째로
없어졌다**는 뜻이다 — §2 가 "거래 이력" 으로 분류한 바로 그 자산이다.
잔액은 사용자가 기억하는 값으로 되돌렸을 뿐 근거는 복원되지 않았다.

### 재발 방지

1. **PITR 을 켠다** (사고 직후 활성화했다). 7일 안의 시점으로 되돌릴 수 있다.
2. 삭제를 안내할 때 **인접한 위험 메뉴를 함께 경고**한다. 이번 사고는 "문서 삭제"
   안내만 하고 바로 옆 "컬렉션 삭제" 를 경고하지 않아 일어났다.
3. 운영 데이터를 손으로 정리하기 전에 **지금 상태를 먼저 적는다.** 이번에 살아난
   것은 그 표 하나였다.
