## 2. U1 — `denied` 배너 카피 (F31 에 그대로 입력)

| 요소 | 최종 문자열 |
|---|---|
| 제목 | `알림이 꺼져 있어요` |
| 본문 (customer, `isOwner == false`) | `알림을 켜면 주문 진행 상황을 바로 받아볼 수 있어요.` |
| 본문 (owner, `isOwner == true`) | `알림을 켜면 새 주문과 환불 요청을 바로 받아볼 수 있어요.` |
| CTA | `알림 켜기` |
| 톤 | `AppColors.warning` (배경 alpha 0.10 + 테두리 + 아이콘 색) |
| 아이콘 | `Icons.notifications_off_outlined` (유지) |

판단 근거
- architect 제안(결정 E-3)을 **그대로 채택**한다. 제목에서 "기기 설정에서"를 제거하여 Android 미요청 집단 / 실제 거부 집단 모두에 참인 문장이 된다.
- 본문은 "~하세요"(요구)가 아니라 "켜면 ~할 수 있어요"(이득)로, CTA `알림 켜기`와 동사가 이어진다. 설정 앱 이동을 암시하지 않으므로 "버튼이 설정 앱으로 안 가도 되는" 2단계 동작과 모순이 없다.
- 설정 앱으로 갈 수 있다는 사실은 배너 본문에 넣지 않는다. 배너 문구가 길어지고, 시트가 먼저 뜨는 다수 경로에서 거짓 예고가 되기 때문이다. 해당 사실은 폴백 발생 시점의 SnackBar(§4)가 전담한다.
- 본문 문장 종결과 톤은 기존 `notDetermined` 본문(`...바로 받아볼 수 있어요.`)과 동일 계열. 두 state 의 본문이 거의 같은 문장 구조가 되어 일관된다.
- 용어: Qoin / Qrator / Log 해당 없음.

### 최종 카피 매트릭스 (참고)

| state | 제목 | 본문 customer | 본문 owner | CTA | 톤 | 아이콘 |
|---|---|---|---|---|---|---|
| `denied` | 알림이 꺼져 있어요 | 알림을 켜면 주문 진행 상황을 바로 받아볼 수 있어요. | 알림을 켜면 새 주문과 환불 요청을 바로 받아볼 수 있어요. | 알림 켜기 | warning | notifications_off_outlined |
| `notDetermined` (**무변경**) | 알림을 켜 보세요 | 주문 진행 상황을 바로 받아볼 수 있어요. | 새 주문과 환불 요청을 바로 받아볼 수 있어요. | 알림 켜기 | info | notifications_none_rounded |

## 3. U2 — `denied` / `notDetermined` 통합 여부

**결정: 시각적으로도 합치지 않고, 현재의 2-state(톤·아이콘·제목 구분)를 유지한다.**

사유
1. **의미가 실제로 다르다 (iOS).** `notDetermined` = 아직 한 번도 안 물어봄(권유, info). `denied` = 사용자가 시트에서 명시적으로 거절했거나 설정에서 껐음(상태 경고, warning). iOS 에서 거절 직후 배너가 info → warning 으로 바뀌는 것은 "결과가 반영됐다"는 가시적 피드백이며 §6 의 피드백 설계가 이 구분에 의존한다. 합치면 이 피드백이 사라진다.
2. **통합의 이득은 이미 확보됐다.** 이득으로 거론된 "Android 에서 사실과 다른 문장 제거"는 제목의 "기기 설정에서" 삭제(§2)로 해결된다. Android 는 `notDetermined` 에 도달할 수 없으므로 항상 `denied` 배너만 보고, 그 문장은 이제 참이다. 통합까지 갈 필요가 없다.
3. **회귀 범위 최소화.** `notDetermined` 배너는 spec 상 변경 금지이고 sub-phase 3 에서 라이브 검증됐다. 통합은 이를 건드린다.
4. **동작 동일성은 UI 에 드러나지 않는다.** 두 state 의 CTA 라벨·위치·동작이 같아져 사용자가 학습할 차이는 없다. 남는 차이는 톤·아이콘·제목 한 줄뿐이며, 이는 상태 전달용(정보)이지 조작 방식 차이가 아니므로 혼동 위험이 없다.
5. `warning` 유지 사유는 spec 결정 E-3 와 같다. 원인과 무관하게 "지금 알림이 오지 않는다"는 사실의 긴급도를 낮추지 않는다.

잔여 부작용(수용): Android 미요청 사용자는 warning 톤을 보지만 실제로는 "아직 안 켠" 상태다. 제목·본문이 비난조가 아니므로 수용한다.

## 4. U3 — 설정 앱 폴백 SnackBar

**필요하다.** 사용자는 `알림 켜기`를 눌렀는데 갑자기 앱이 설정 앱으로 전환된다. 사전 안내가 없으면 앱이 튕긴 것처럼 보이고, 설정 앱에서 무엇을 해야 하는지도 모른다.

| 항목 | 값 |
|---|---|
| 카피 | `기기 설정에서 알림을 허용해 주세요` |
| 노출 시점 | 설정 앱 폴백 직전 (E-2 `denied`/`denied` 경로, 세션 가드 경로, F29 예외 경로 **3곳 공통**) |
| 배경 | **`AppColors.primary`** (neutral) |
| 텍스트 | `AppColors.onPrimary`, fontSize 13 / w500 (기존 SnackBar 와 동일) |
| behavior / duration | `floating` / **4초** (기존 3초 → 설정 앱 복귀 후에도 잠깐 보이도록) |
| 아이콘·액션 | 없음 |

### 톤 결정: architect 제안(`AppColors.info`)에서 변경 — `AppColors.primary`

- `info`(#0EA5E9) 위 `onPrimary`(흰색) 텍스트는 대비 약 2.8:1 로 가독성 기준(4.5:1) 미달이다. 13px 본문 텍스트에는 부적합.
- 같은 화면에서 `info` 는 이미 `notDetermined` 배너 톤이다. 같은 토큰을 SnackBar 에도 쓰면 "정보 배너"와 "전환 안내"가 혼동된다.
- `primary`(미드나잇 네이비) + 흰 글씨는 대비가 충분하고, 성공도 실패도 아닌 중립 안내라는 성격에 맞다. error/warning 색을 피한다는 제약도 충족. 신규 토큰 없음.
- architect 가 `info` 를 강하게 원하면 대안은 가능하나 접근성상 비권장. (§8 확인 사항)

### 카피 판단
- "~해 주세요" 요청형, 해요체. 실패 표현("실패", "못했어요") 금지.
- 설정 앱 안에서 해야 할 행동(허용)을 명시. "Qradar" 앱명은 SnackBar 에서는 생략 — 설정 앱 목록에서 앱을 찾는 안내가 아니라 전환 이유 안내이므로 짧게 유지.
- `AppSettings.openAppSettings()` 자체가 실패했을 때의 기존 에러 SnackBar(`설정 화면을 열 수 없어요`, `AppColors.error`)는 **변경 없이 유지**. 이는 진짜 실패이므로 error 톤이 맞다. 같은 화면에서 안내 SnackBar 와 에러 SnackBar 는 색으로 구분된다.

### 구현 주의 (developer)
- 안내 SnackBar 표시 → 곧바로 `openAppSettings()` 호출하면 사용자는 SnackBar 를 거의 못 보고 설정 앱으로 넘어간다. 앱 복귀 시점에도 일부 남도록 duration 4초로 늘리고, **안내 후 약 500ms 대기 뒤 설정 앱 호출**을 권장한다 (이 구간도 `_requestingPermission` 안이므로 스피너 유지, 중복 탭 없음). 지연 도입이 부담이면 생략 가능 — 필수 아님.
- 표시 전 `clearSnackBars()` 로 이전 SnackBar 제거(연속 탭 시 큐 누적 방지).
- 기존 `_showSnack` 는 error 배경 고정이므로, 배경을 파라미터화하거나 안내용 별도 메서드를 둔다. 색은 `AppColors` 토큰만.

## 5. U4 — 2단계 동작 중 로딩 표현

**판단: 현재 사양(비활성 + 16x16 스피너)으로 충분. 단계별 피드백 추가하지 않는다.**

| 구간 | 사용자가 보는 것 | 비고 |
|---|---|---|
| ① `requestPermission()` | OS 시트가 배너 위를 덮음 (iOS/Android 공통) | 스피너는 시트 뒤에 있어 어차피 거의 안 보임. 시트 자체가 진행 표시 |
| ② 시트가 안 뜬 경우 | 스피너가 수백 ms 보임 | 즉시 반환되므로 짧음 |
| ③ 폴백: SnackBar → 설정 앱 | 스피너 + SnackBar | SnackBar 가 "왜 전환되는지" 설명하므로 스피너 문구 불필요 |

- 길어진 구간의 대부분은 OS 시트(사용자 조작 시간)이며 앱이 제어하는 대기가 아니다. 앱 측 대기는 수백 ms 수준이다.
- 단계별 문구 교체(`요청 중…` → `설정 여는 중…`)는 순간적으로 바뀌어 읽히지 않으며, 스크린리더 liveRegion 노이즈만 늘린다.
- 버튼 비활성은 기존 스타일 그대로 `disabledBackgroundColor: primary` / `disabledForegroundColor: onPrimary` 라 비활성 시에도 색이 유지되고 스피너가 선명하다. 변경 없음.
- Semantics label `알림 권한을 요청하는 중` 유지 (F34). 폴백 구간은 요청 처리의 연속으로 본다.
- 추가 방어: 로딩 중 뒤로가기는 막지 않는다 (기존 동작, `mounted` 체크로 처리).

## 6. 항목 5 — `notDetermined` 에서 거부당한 경우 (iOS, 설정 앱 미오픈)

**별도 SnackBar·다이얼로그 추가하지 않는다. 배너의 state 전환을 피드백으로 사용한다.**

거부 직후 화면 변화
1. 스피너 해제 → CTA 가 다시 `알림 켜기` 로 복귀.
2. 배너가 `notDetermined`(info, `notifications_none_rounded`, `알림을 켜 보세요`) → `denied`(warning, `notifications_off_outlined`, `알림이 꺼져 있어요`) 로 바뀐다. 색·아이콘·제목이 한꺼번에 바뀌므로 "버튼이 안 먹었다"가 아니라 "결과가 반영됐다"로 읽힌다.
3. `Semantics(liveRegion: true)` 로 스크린리더가 바뀐 배너 내용(`알림이 꺼져 있어요. 알림을 켜면 …`)을 자동으로 읽는다.

SnackBar 를 추가하지 않는 이유
- 사용자가 방금 시트에서 **명시적으로 거절**했다. 거절 직후 앱이 다시 "알림을 허용해 주세요" 류 문구를 띄우면 재설득으로 느껴져 §E-2 가 피하려던 침해성을 UI 로 되살린다.
- 이 상태의 다음 탭은 곧바로 설정 앱 폴백(+§4 안내 SnackBar)으로 이어지므로 안내 지점이 이미 존재한다.
- 거절 확인용 "알림이 꺼진 채로 유지됩니다" 류 문구는 배너 제목과 중복.

이 경로는 iOS 전용이므로 **이 판단은 iOS 에서만 의미가 있다**. Android 는 시트 거부 직후에도 E-2 규칙상 설정 앱으로 폴백한다 (§8-2 참고).

## 8. 접근성

- 배너 `Semantics(container: true, liveRegion: true)` 유지. 카피 변경으로 낭독문이 바뀐다.
  - customer `denied`: "알림이 꺼져 있어요. 알림을 켜면 주문 진행 상황을 바로 받아볼 수 있어요. 알림 켜기 버튼"
  - owner `denied`: "알림이 꺼져 있어요. 알림을 켜면 새 주문과 환불 요청을 바로 받아볼 수 있어요. 알림 켜기 버튼"
  - 제목·본문 모두 "알림" 어휘로 시작해 반복이 있으나 의미 중복은 없다. 본문의 선행 조건절("알림을 켜면")이 CTA 와 이어져 낭독 흐름이 자연스럽다.
- 두 state 의 CTA 낭독이 모두 `알림 켜기` 로 같아졌다. 구분은 제목(낭독 첫 문장)으로 충분하다.
- iOS 거부 직후 liveRegion 이 `denied` 문구를 자동 낭독 (§6).
- 안내 SnackBar 는 Flutter 기본 SnackBar 의 접근성 announce 에 맡긴다. 추가 Semantics 불필요.
- 터치 타깃: 기존 CTA(`minimumSize 96x40`, `tapTargetSize: padded`) 유지.
- 색 대비: SnackBar `primary` / `onPrimary` 충분. 배너 본문 `textBody` on warning 10% 배경은 기존과 동일.

## 9. developer 전달사항

1. **F31 확정 문자열**
   - `denied` 제목: `알림이 꺼져 있어요`
   - `denied` 본문 customer: `알림을 켜면 주문 진행 상황을 바로 받아볼 수 있어요.`
   - `denied` 본문 owner: `알림을 켜면 새 주문과 환불 요청을 바로 받아볼 수 있어요.`
   - CTA(두 state 공통): `알림 켜기` — `_denied ? '설정 열기' : '알림 켜기'` 삼항 제거
2. **본문 분기 구조**: 현재 `_denied ? 고정문 : (isOwner ? A : B)` → `isOwner` 분기를 `denied` 쪽에도 신설. `notDetermined` 문자열은 한 글자도 바꾸지 않는다.
3. **F34 확인**: 스피너 Semantics label `알림 권한을 요청하는 중` 유지.
4. **안내 SnackBar 문자열**: `기기 설정에서 알림을 허용해 주세요` (배경 `AppColors.primary`, 텍스트 `AppColors.onPrimary`, 4초, floating). 폴백 3경로(E-2 / 세션 가드 / F29 예외) 모두 동일 문자열·동일 스타일.
5. 기존 에러 SnackBar(`AppColors.error`) 및 그 문자열 3종(`설정 화면을 열 수 없어요`, `설정을 저장하지 못했어요...`)은 변경 없음.
6. iOS `notDetermined` 거부 후에는 SnackBar 를 **띄우지 말 것** (§6).
7. 신규 색상·신규 위젯 없음. `Color(0x...)` / `Colors.*` 금지.
8. 테스트 정합: spec T-B9 는 위 문자열과 일치 확인. 추가 확인 — 폴백 시 SnackBar 노출(T-B5), iOS 거부 시 SnackBar 미노출(T-B11), 스크린리더 liveRegion 낭독(선택).

### 라이브 검증 추가 항목

**T-B17 (신규)** — Android 에서 `denied` 배너의 `알림 켜기` 를 탭해 OS 시트가 뜨고, 거기서 **거부**했을 때의 체감을 확인한다.
확인 포인트: ① 안내 SnackBar `기기 설정에서 알림을 허용해 주세요` 가 읽히는가 ② 설정 앱 전환이 침해적으로 느껴지는가.
②가 문제로 판정되면 결정 E-2 를 재검토한다 (대안: 설정 앱 전환을 CTA 2회차부터로 미루기). **기능 결함이 아닌 체감 평가 항목이므로 릴리스 차단은 아니다.**

## U3 개정 (2026-10-21, 라이브 검증 중) — 1회차 탭은 안내만

spec 결정 E-2 가 개정되면서 SnackBar 의 역할이 둘로 갈렸다. **카피·색상·길이는 변경 없다.**

| 상황 | SnackBar | 설정 앱 전환 |
|---|---|---|
| 1회차 탭, `statusBefore == denied`, 결과 `denied` | ○ | **× (개정)** |
| 2회차 이후 탭 (세션 가드) | ○ | ○ (500ms 후) |
| `statusBefore == notDetermined`, 결과 `denied` (iOS) | × | × |
| 설정 앱 열기 자체 실패 | error 톤 `설정 화면을 열 수 없어요` | — |

사유: 사용자가 OS 시트에서 방금 `거부` 를 누른 직후 설정 앱으로 전환되는 것은 거절 의사를 무시하는 동작이다. iOS 경로에서는 이미 전환하지 않고 있어 플랫폼 간 일관성도 없었다. 1회차에는 안내만 남기고, 경로가 필요한 사용자는 재탭으로 도달한다 (세션 가드가 2회차를 설정 앱으로 보낸다).

안내 SnackBar 는 전환이 없는 1회차에서도 **그대로 유지**한다. 영구 차단된 사용자는 시트를 보지 못하므로, 이 한 줄이 유일한 피드백이자 다음 행동(재탭)의 단서가 된다.
