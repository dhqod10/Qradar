## 0. 먼저 읽을 것 — 설계 중 발견한 사실 7건

> 이 중 0-1 ~ 0-3 은 **지시받은 문구를 그대로 쓰면 어떤 상태에서는 거짓이 된다**는 발견이다. 문구 규칙으로 해결했고 §9 에 반영했다.

### 0-1. 「영업과 주문은 그대로 계속됩니다」 는 **승인 이력이 있는 매장에서만 참**이다

`canSellNow = (status=='approved') || (status=='pending' && approvedAt != null)`. 핵심 수정 확인 단계의 안내는 **매장의 서버 현재 상태로 3갈래**여야 한다.

| 서버 현재 상태 | 영업·주문 | 쓸 수 있는 문구 |
|---|---|---|
| `approved` | 계속됨 | 지시받은 문구 그대로 (영업과 주문은 그대로 계속됩니다) |
| `pending` **+** `approvedAt != null` (이미 수정 검토 중) | 계속됨 | 위와 동일 |
| `pending` **+** `approvedAt == null` (첫 승인 대기) | **원래 안 됨** | 「영업과 주문은 계속돼요」 **금지**. 「아직 첫 승인을 기다리는 매장이에요」 |
| `rejected` | **안 됨** | 「재제출」 문구. 영업 계속 언급 금지 |

### 0-2. 브랜드 가맹 매장의 점주에게 **핵심 폼은 원래 없다** (앱과 동일)

`my_store_page.dart` — `brandId != null` 이면 `_BrandStoreDetailView` 가 **「운영 정보 수정」 버튼 하나뿐**이고 배너 「매장 핵심 정보는 브랜드 본사가 관리해요.」 를 단다. 반려 시에도 「재제출은 브랜드 본사에서 진행됩니다.」 → **웹도 같게 한다**(U2). 핵심 폼은 **개인 매장 점주 전용**.

### 0-3. `temporaryClosed` (임시 휴무) 는 **주문을 막지 못한다**

`lib/` · `functions/src` 어디에서도 `temporaryClosed` 를 판매 판정에 읽지 않는다(엔티티·모델·폼에만 존재). 앱 폼도 「활성화 시 잠시 휴무 상태로 표시돼요.」 로만 적고, 앱 코드 주석이 「임시 휴업을 안내하지 않는다 — 주문을 막지 못하므로 안내하면 거짓」 이라 못박았다. → 웹 스위치 옆에 「주문 접수를 막는 기능이 아니에요」 를 **명시**한다(U8).

### 0-4. 브랜드의 `산하 매장` 쿼리는 `status=='approved'` 매장만 돌려준다 (R-B3)

미승인 가맹점은 목록에 **없다.** 빈 목록을 「가맹점이 없다」 로 읽으면 거짓이다 → 캡션으로 명시(BR12).

### 0-5. 브랜드 핵심 수정 후 노출 영향은 **확인된 근거가 없다**

매장은 `canSellNow` 가 명문화돼 있지만 브랜드(`name`/`description` 수정 → `status='pending'`)에 대응하는 판정은 이번 조사에서 확인하지 못했다. **「영업 계속」 류 문구를 브랜드에는 쓰지 않는다**(U5). 가격 오버라이드가 `pending` 으로 회귀하는 동안 **기존 승인 가격이 유지되는지**도 미확인(U6) → 「반영」 시점만 사실대로 적는다.

### 0-6. 주소를 바꾸려면 **좌표**도 필요하다

`address` 만 바꾸면 `location(GeoPoint)` 이 어긋난다. 앱은 Kpostal 검색 + 좌표 변환(「좌표 변환에 실패했어요」)을 쓴다. 웹은 시크릿 없이(절대규칙 4) 이를 해결할 근거가 없다 → **1차 읽기 전용** 권고(U1).

### 0-7. 현재 코드에서 **바꿔야 하는 문구·구조** (developer 가 놓치기 쉬운 곳)

`index.html` `<title>` 「Qradar 관리자 콘솔」, 주석 「/admin/index.html」 · `readUserRole` 이 `{admin:bool}` 만 돌려줌(문서 부재도 비admin 으로 처리) · `renderNotAdmin` 이 비admin **전부**를 5초 뒤 로그아웃 · `S.counts` 가 admin 4건수 고정 · `route()` 의 `else → #/dashboard`. 상세는 §16.

## 2. 추가 원칙 (이 문서 한정)

1. **한 폼은 한 종류의 결과만 낸다.** 「즉시 반영」 폼과 「검토 요청」 폼을 한 화면에서 같은 저장 버튼으로 묶지 않는다. 저장 버튼 라벨이 곧 결과 예고다 — `저장`(즉시) vs `검토 요청 보내기…`(재승인).
2. **결과를 모르는 채 누르게 하지 않는다.** 재승인이 걸리는 버튼은 라벨에 말줄임(`…`)과 `재승인 필요` 칩을 붙이고, 확인 모달에서 **서버가 읽은 현재 상태 기준**으로 결과를 사실대로 적는다(§0-1).
3. **문구는 앱 것을 값으로 쓴다.** spec §16 지시대로 앱 문구가 있으면 그대로(§0 의 보강 문구 제외). 이 문서에서 **「(신규)」** 표시가 붙은 문구만 웹에서 새로 쓴 것이고, developer 는 앱 문구가 따로 있는지 한 번 더 확인한다.
4. **역할 표시는 상시.** 사용자가 어떤 권한으로 보고 있는지는 사이드바에서 항상 보인다(UI4). 그렇다고 이를 **보안 표시로 쓰지 않는다** — 문구에 「접근 제한」 「차단」 금지(admin §9).

토큰 사용에서 **추가로 확정한 매핑** (모두 기존 변수):

| 신규 요소 | 배경 | 테두리 | 글자 | 비고 |
|---|---|---|---|---|
| 스위치 켜짐 | 트랙 `--primary` | — | 라벨 `--text-heading` | 노브 `--on-primary` |
| 스위치 꺼짐 | 트랙 `--border` | — | 라벨 `--text-muted` 금지 → `--text-heading` | 노브 `--surface-elevated`. **「켜짐/꺼짐」 글자 항상 병기**(색만으로 구분 금지) |
| 탭 활성 | 투명 | 하단 2px `--primary` | `--text-heading` | 비활성 글자 `--text-body` (muted 아님: 탭은 본문 정보) |
| 고정 저장 바 | `--surface-elevated` | 상단 `1px --border` | — | 그림자 `var(--shadow)` 약하게 대신 선 하나만 |
| 변경 있음 표식 | 점 6px `--primary-bright` | — | 「변경 N개」 `--text-heading` | 색+글자 병기 |
| 준비 중 카드(§11) | `--surface` | **점선** `1px dashed --border` | `--text-body` / 설명 `--text-muted` | 호버·포커스 효과 없음 |
| 재승인 칩 | `--surface-elevated` | `--border` | `--text-heading` | `.a-chip` 변형(글자 muted 대신 heading) |

## 3. 역할별 셸 · 네비게이션 · 화면 목록

### 3-1. 셸 골격 변경점 (admin §3-2 대비)

골격(232px + 1080px)은 동일. 바뀌는 곳은 **사이드바 3군데**뿐이다.

```
┌────────────────┐
│ [Q] Qradar     │  로고 블록 (불변)
│ 점주 콘솔      │  ← 13px muted. 「관리자 콘솔」 고정 문구 → 「{역할} 콘솔」
│                │
│ 모카 강남점    │  ← (신규) 컨텍스트 블록: brand=브랜드명 / owner=매장명. 14px/700, 말줄임
│ ● 승인됨       │     상태 배지 (admin §4-2). admin·customer 는 이 블록 없음
│                │
│ 매장           │  ← 네비 그룹 (역할별, §3-2)
│  내 매장       │
│ 운영 …         │
│                │
│ ────────────── │
│ me@example.com │  계정 영역: 이메일(말줄임)
│ [점주]         │  ← (신규) 역할 칩. 기존 「관리자」 텍스트 라벨 자리
│ [ 로그아웃 ]   │
└────────────────┘
```

| 요소 | 명세 |
|---|---|
| 역할 칩 | `.a-chip` 형태, 글자 `--text-heading` 600, 최소 높이 24px. 문구: **관리자 / 브랜드 / 점주 / Qrator**(U4). `aria-label="현재 역할: 점주"` |

### 3-2. 역할별 네비게이션 (spec §8.2 확정안 + 전제 미충족 시 축소)

> 원칙(승계): **해당 역할의 항목만 그린다. 없는 메뉴를 비활성으로 보여주지 않는다.** 이 원칙은 보안이 아니라 혼동 방지다.

```
admin                      brand                       owner                       customer
─────────────────────      ─────────────────────       ─────────────────────       ─────────────────────
운영                       브랜드                      매장                        내 정보
  대시보드                   브랜드 정보                 내 매장                     프로필
승인 큐                      검토 현황                 운영                          주문 내역 (Log)
  브랜드        [n]        메뉴                          매출                        Qoin
  매장          [n]          마스터 메뉴                 받은 평가
  마스터 메뉴 [읽기][n]      서브 카테고리             메뉴
  매장 커스텀 [읽기][n]      옵션 그룹                   메뉴 관리
조회                       가맹점                        서브 카테고리 ┐ 개인 매장일 때만
  매장 목록                  산하 매장     [읽기]        옵션 그룹     ┘ (§3-4)
  Qoin 현황
```

| 역할 | 항목 → 해시 | 기본 진입 |
|---|---|---|
| admin | 기존 7개 그대로 (`#/dashboard` `#/brands` `#/stores/pending` `#/menus` `#/overrides` `#/stores` `#/qoin`) | `#/dashboard` |
| brand | 브랜드 정보 `#/b/info` · 검토 현황 `#/b/tracking` · 마스터 메뉴 `#/b/menus` · 서브 카테고리 `#/b/subcats` · 옵션 그룹 `#/b/options` · 산하 매장 `#/b/stores` | `#/b/info` |
| owner | 내 매장 `#/o/store` · 매출 `#/o/sales` · 받은 평가 `#/o/reviews` · 메뉴 관리 `#/o/menus` · 서브 카테고리 `#/o/subcats` · 옵션 그룹 `#/o/options` | `#/o/store` (매출이 아니라 내 매장: 상태 배너가 먼저 보여야 한다) |
| customer | 프로필 `#/u/profile` · 주문 내역(Log) `#/u/log` · Qoin `#/u/qoin` | `#/u/profile` |

- **건수 배지**는 admin 승인 큐 4개에만 있다(승계). brand/owner/customer 항목에는 배지를 달지 않는다 — 검토 현황의 반려 건수는 N회 조회가 필요해(R-B11) 사이드바에서 상시 갱신하기에 비싸다.
- **「읽기」 칩**(승계): admin `마스터 메뉴` `매장 커스텀`, brand `산하 매장`. customer 의 3항목은 전부 읽기 전용이므로 항목마다 칩을 달지 않고 **그룹 라벨 옆에 한 번** 「읽기」 칩을 둔다(반복 소음 방지).
- 활성 항목: 배경 `--primary` / 글자 `--on-primary`, `aria-current="page"` (승계).

| 사이드바 | 위 §3-1 의 3군데(부제·역할 칩·컨텍스트 없음) 외 동일 |

| 페이지 `<title>` / 로그인 카드 제목 | 「Qradar 관리자 콘솔」 → 「Qradar 콘솔」 |

### 3-4. 전제 미충족 시 네비 축소 규칙 (spec §8.3 + S6)

전제가 없으면 의존 항목은 **네비에서 빼고**, 남는 항목 하나가 이유를 설명한다. 「눌러도 막다른 길」 인 항목을 늘어놓지 않는다.

| 상황 | 네비에 남는 것 | 본문 |
|---|---|---|
| brand · `users.brandId` 없음 | 그룹 「시작하기」 → 항목 **「브랜드 연결」** `#/b/info` 하나 | GT1 (§7-1) |
| owner · 매장 0건 | **「내 매장」** `#/o/store` 하나 | GT3 (§7-3) |
| owner · 매장 로드 중 | 「내 매장」 + 메뉴 관리 같은 **고정 항목은 그리되**, 개인 매장 전용 2항목(서브 카테고리/옵션 그룹)은 매장 유형이 확정될 때까지 **그리지 않는다.** 마지막 항목이라 나타나도 위쪽이 밀리지 않는다 | |
| owner · 브랜드 가맹 매장 | 서브 카테고리 / 옵션 그룹 **없음**(앱과 동일: 개인 매장만) | |
| 전제 해소(claim 성공 등) | 서버 재확인 후 **전체 네비로 재구성** | |

### 3-5. 해시 규칙 · 라우팅 전환 (admin §7 확장)

- 1단 네임스페이스: `b` brand / `o` owner / `u` customer. admin 은 없음.
- **자기 역할 밖의 해시** → 자기 기본 진입으로 정규화. 예: owner 가 `#/b/menus` 를 열면 `#/o/store`. 빈 화면·에러 화면이 되지 않는다. 이 리다이렉트는 **편의이며 보안이 아니다**(문구 어디에도 「접근할 수 없어요」 를 쓰지 않는다. 조용히 이동만).
- 같은 역할 안의 **알 수 없는 해시** → 자기 기본 진입.
- **저장 안 한 변경이 있는 폼**에서 해시가 바뀌려 하면: 이동을 되돌리고 확인 모달(§6 N15). 뒤로가기도 동일. 탭 닫기/새로고침은 `beforeunload`.
- 쓰기 in-flight 중에는 이동을 막지 않되 `beforeunload` 확인(승계).
- 상세/폼 진입 시 목록에서 받은 값을 임시로 보여주지 않고 **즉시 스켈레톤**(승계).

### 5-3. G2 판정 실패 — fail-closed (admin §5 A0-d 승계)

문구·동작은 승계: 「권한을 확인하지 못했어요」 + error 배너 + 사유(네트워크 / 읽기 거부 / 알 수 없음) + `[다시 시도]` `[로그아웃]`. **「일단 열어주고 실패한 카드만 에러」 로 처리하지 않는다.** 바뀌는 점은 두 가지뿐이다.

- 「…콘솔을 열 수 없어요」 의 주어가 관리자에서 모든 역할로 확장되므로 문구에서 「관리자」 를 쓰지 않는다. 본문: 「계정 정보를 불러오지 못해 콘솔을 열 수 없어요.」 (승계 문구 그대로 — 원래부터 역할을 말하지 않는다)
- 「읽기 거부」 사유는 본인 문서 읽기가 거부된 **이상 상황**이므로 사유 줄 아래에 13px muted 한 줄 추가: 「계정 정보를 읽을 수 없는 상태예요. 계속되면 운영 담당자에게 문의해주세요.」 (원본 에러·스택 노출 금지 승계)

### 5-4. G3 모르는 role — 5초 자동 로그아웃의 **유일한 잔류 지점**

**전환 설명**: 지금의 `renderNotAdmin` 은 「admin 이 아니면 전부」 5초 뒤 로그아웃한다. 역할별 콘솔에서 admin 이 아닌 계정은 **정당한 사용자**(brand·owner·customer)이므로, 그 화면은 **「role 값이 모르는 문자열일 때」** 로 대상이 줄어든다. 자동 로그아웃의 사유(공용 PC 방치 방지, 접근 차단 수단 아님 — 기존 코드 주석 그대로)는 유지하되 **대상만 좁힌다.**

```
          ┌────────────────────────────┐
          │        [Q 로고 48px]        │
          │ 이 계정의 권한 정보를       │   <- 18px/700
          │ 확인할 수 없어요            │
          │                            │
          │ 계정 정보에 콘솔이 모르는   │   <- 14px body
          │ 권한 값이 들어 있어요.      │
          │ 현재 계정:                  │
          │ name@example.com           │   <- 14px/600
          │ 권한 값: superadmin         │   <- 13px muted, 최대 40자 말줄임, textContent 로만 삽입
          │ 운영 담당자에게 문의해주세요.│
          │                            │
          │ 5초 후 자동으로 로그아웃돼요.│   <- 13px muted (카운트다운)
          │ [   지금 로그아웃   ]       │   <- Secondary 전폭 44px
          └────────────────────────────┘
```

| 항목 | 명세 |
|---|---|
| 판정 | `users/{uid}` 읽기 **성공** + `role` 필드가 **존재**하는데 `admin`/`brand`/`owner`/`customer` 4개 중 하나가 아님 (빈 문자열·null·숫자·대소문자 불일치 포함) |
| 문구 | 사실만. 「차단」 「접근 거부」 금지. 「권한 값」 줄은 지원 문의를 돕기 위한 것(본인 계정 정보) |
| 자동 로그아웃 | 5초 카운트다운 + 「지금 로그아웃」 버튼 (현 구현 유지). 인증 세대(`authGen`)가 바뀌면 취소(현 구현 유지) |
| 로그아웃 후 | 로그인 화면 info 배너: 「이 계정의 권한을 확인할 수 없어 로그아웃했어요.」 (현 `NOT_ADMIN_NOTICE` 교체) |
| 상태 3종 | loading = 해당 없음(판정 자체가 결과) / error = 해당 없음 / empty = 해당 없음 |

> `role: null` 처럼 「필드는 있으나 값이 null」 은 Rules `userDoc().get('role','customer')` 가 `null` 을 돌려주므로 **어느 역할도 아니다**. 콘솔은 이를 「부재」 가 아니라 「모르는 값」 으로 분류한다(권한을 임의로 customer 로 올려 해석하지 않는다). 분류 경계는 §16 DV-3.

### 5-5. 문서 부재 → customer 셸 (정상 상태, **게이트가 아님**)

- 셸 상단에 안내를 붙이지 않는다. 오류처럼 보이면 안 된다.
- CU1 프로필 카드에서만 값이 `-` 로 비고 캡션 한 줄: 「아직 프로필 정보가 없어요. 앱에서 프로필이 만들어지면 여기에 나타나요.」 (error 가 아님. 배지·`--error` 사용 금지)

### 5-6. G5 역할 변경 감지 — 폴링 없음, `permission-denied` 가 계기

```
섹션 주 read (또는 write) 가 permission-denied
        │
        ▼
 users/{uid} 재확인 (단일 비행: 동시에 실패한 카드 N개가 읽기를 N번 하지 않는다)
        │
        ├─ role·brandId 가 셸을 열 때와 같음 ──► 평범한 「권한이 없어 불러올 수 없어요」 (해당 카드만)
        ├─ role 이 정상 값으로 달라짐 ─────────► 셸 재구성 + 안내 배너 (아래)
        ├─ 문서 부재/필드 부재로 달라짐 ───────► customer 셸로 재구성 + 같은 배너
        ├─ role 이 모르는 값으로 달라짐 ───────► G3
        ├─ 재확인 읽기 자체가 실패 ────────────► 해당 카드에 오류 + 「권한을 다시 확인하지 못했어요」 (셸 유지, 쓰기 폼 열지 않음)
        └─ 인증이 사라짐 ──────────────────────► G4
```

**재구성 시 화면**: 사이드바 전체를 새 역할의 네비로 교체, 역할 칩 갱신, 해시를 새 역할의 기본 진입으로 정규화, 본문 상단에 **닫을 수 있는 info 배너**(영구 잔류, X 로 닫음):

```
 ┌ info 배너 ───────────────────────────────────────────────────────────┐
 │▌ 권한이 바뀌었어요. 화면을 다시 구성했어요.   (점주 → Qrator)    [닫기] │
 └──────────────────────────────────────────────────────────────────────┘
```

| 항목 | 명세 |
|---|---|
| 문구 | 「권한이 바뀌었어요. 화면을 다시 구성했어요.」 (spec §9.3 그대로) + 괄호에 이전 → 새 역할 칩 문구 |
| 열려 있던 폼 · 모달 | **닫고 입력은 버린다.** 이전 역할의 폼은 새 역할에서 의미가 없다. 버려졌음은 배너 2행에 한 줄: 「열려 있던 입력은 저장되지 않았어요.」 (입력이 실제로 있었을 때만) |
| 진행 중이던 쓰기가 거부됨 | 성공으로 표시하지 않는다. 폼 안 배너 「저장되지 않았어요. 권한이 바뀌었어요.」 후 재구성 (입력 보존은 하지 않음 — 위와 같은 이유) |
| 브랜드 연결 변경 | role 은 같고 `users.brandId` 만 바뀐(비워진 포함) 경우도 재구성 (컨텍스트 블록·데이터가 낡았으므로) |
| 재확인 횟수 | 같은 세션에서 연속 실패로 재확인이 폭주하지 않도록 3초 안의 중복은 묶는다(DV-4) |
| 문구 금지 | 「권한이 제거되어」 「접근이 막혀」 등 UI 가 권한을 집행한 듯한 표현 금지 |

| 상태 | 표시 |
|---|---|
| loading | 재확인 중에는 해당 카드를 스켈레톤으로 되돌리지 않고 기존 오류 블록의 `다시 시도` 를 「확인 중…」 으로 (admin §A0-d 와 같은 방식) |
| error | 재확인 실패 시 오류 블록 문구: 제목 「불러오지 못했어요」, 설명 「권한을 다시 확인하지 못했어요. 연결을 확인한 뒤 다시 시도해주세요.」 |
| empty | 해당 없음 |

## 7. 섹션 전제 게이트 4종 (셸 유지)

셸과 역할 칩은 그대로 두고 **본문만** 안내 카드(N9)로 바꾼다. 데이터 요청은 게이트 판정에 필요한 것 외에는 보내지 않는다. 「안내벽」 이 아니라 **다음에 할 일을 알려주는 화면**이다.

### 7-1. GT1 — brand 인데 `users.brandId` 가 비어 있음 (B10)

`brands where submittedBy==uid` 를 조회해 분기한다. 이 조회가 끝나기 전에는 어느 분기도 그리지 않는다.

```
 (분기 a: 내가 제출한 브랜드 1건)
 ┌──────────────────────────────────────────────┐
 │ 브랜드 연결을 마치지 못했어요                  │  18px/700
 │ 등록한 브랜드 「모카하우스」 가 있어요.        │  14px
 │ 아직 이 계정에 연결되지 않았어요. 연결하면    │
 │ 브랜드를 관리할 수 있어요.                    │
 │ 등록한 브랜드는 그대로 있어요. 다시 등록하지   │  13px muted (앱 문구)
 │ 않아도 돼요.                                  │
 │ [   브랜드 연결   ]                           │  Primary
 └──────────────────────────────────────────────┘
```

| 분기 | 본문 | 버튼 |
|---|---|---|
| a. 제출 브랜드 1건 | 위 와이어 | `[브랜드 연결]` → `claimSubmittedBrand` 1회. in-flight 「연결하고 있어요…」(앱 「브랜드를 연결하고 있어요」) |
| b. 0건 | 「등록한 브랜드를 찾을 수 없어요」 + 「브랜드 등록은 앱에서 먼저 완료해주세요. 웹에서는 등록할 수 없어요.」 | 없음 (**등록 폼·링크 만들지 않음**, N4). `[다시 확인]` Secondary (조회 재실행) |
| c. 2건 이상 | 앱 문구 「등록한 브랜드가 N개 있어요. 가장 먼저 등록한 「이름」 으로 연결을 시도해요.」 + 「같은 계정으로 등록된 브랜드가 더 있어서 관리자가 확인할 거예요」 | `[브랜드 연결]` (앱과 같은 선택 규칙 — developer 가 `brand_id_missing_view.dart` 와 일치시킨다, DV-9) |

| 결과 | 표시 |
|---|---|
| 성공 | 서버에서 `users/{uid}` **재읽기** 후 `brandId` 확인되면 전체 네비로 재구성 + 토스트 「브랜드 「이름」 에 연결했어요」(앱 문구). 응답만 믿고 재구성하지 않는다 |
| `already_linked` | error 배너 「이 계정은 이미 다른 브랜드에 연결돼 있어요」 + `[새로고침]`(users 재읽기) |
| `not_brand_account` | 「브랜드 계정이 아니에요」 + 「계정 역할이 바뀐 것 같아요…」(앱 문구) → G5 재확인 |
| `not_submitter` | 「이 브랜드는 내 계정으로 등록한 브랜드가 아니에요」 — **재시도 버튼 없음**(재시도해도 같다) |
| `brand_not_found` | 「브랜드가 삭제됐을 수 있어요. 다시 확인해 볼까요?」 + `[다시 확인]` |
| 네트워크/기타 | 「브랜드 연결을 마치지 못했어요」 + 「잠시 후 다시 시도해주세요」 + `[다시 시도]` |

| 상태 | 표시 |
|---|---|
| loading | 안내 카드 자리 스켈레톤 + 「브랜드 정보를 확인하고 있어요」(앱 문구). 버튼 그리지 않음 |
| error | 조회 실패: 「브랜드 정보를 확인하지 못했어요」 + `[다시 시도]`. **a 분기 버튼을 그리지 않는다**(모르는 채로 연결 시도 금지) |
| empty | 분기 b 가 곧 empty |

### 7-2. GT2 — 브랜드 승인 상태 배너 (게이트 아님, 상시 배너)

brand 모든 화면 헤드 아래에 1개. **쓰기는 막지 않는다**(Rules 가 보유자 쓰기를 허용; 이 배너는 사실 안내).

### 7-4. GT4 — owner 의 매장이 승인 전 (화면은 열고 상태 배너)

### OW6 · OW7. 메뉴 관리 — 개인 매장 (`approved` 일 때만 노출)

- 가격·이름·사진 등은 **읽기 전용 텍스트**. 입력 컨트롤 없음. 「메뉴 추가」 「편집」 「삭제」 **없음**.

## 9. 매장 정보 수정 — 두 개의 폼 (Q3 정정 반영, 이 문서의 핵심)

### 9-0. 구조 원칙

| | **폼 ① 운영 정보** (OW2) | **폼 ② 핵심 정보** (OW3) |
|---|---|---|
| 해시 | `#/o/store/ops` | `#/o/store/core` |
| 필드 | `phone` `description` `notice` `excludedMainCategories` `businessHours` `temporaryClosed` `closedDates` `imageUrls`(+`imageUrl`) | `name` `address`+`location` `menuCategories` `businessRegistrationNumber` |
| 결과 | **즉시 반영.** `status`·승인 메타 **무변경** | `status='pending'` 회귀 → 관리자 재승인 대상 |
| 저장 버튼 | `저장` | `검토 요청 보내기…` (`rejected` 면 `재제출하기…`) |
| 확인 단계 | **없음** (안내 없이 저장) | **변경 확인 모달** (§9-3) |
| 누가 쓰나 | 개인 매장 · **브랜드 가맹 매장 점주 모두** | **개인 매장 점주만** (0-2, U2) |
| 앱 대응 | `toFirestoreForOperationUpdate` | `toFirestoreForCoreUpdate` |

**분리를 UI 구조로 강제한다**: 서로 다른 라우트·서로 다른 폼 요소·서로 다른 저장 버튼이다. 한 화면에서 두 묶음을 편집하는 탭·아코디언을 만들지 않는다. 폼 ① 에 핵심 필드 입력칸이 **하나도 없고**, 폼 ② 에 운영 필드 입력칸이 하나도 없다 — 그래야 전화번호만 고친 사용자의 payload 에 핵심 키가 섞일 수 없다. 두 폼 사이를 오갈 때 저장 안 한 변경은 N15 로 확인한다.

**진입 조건과 상태별 상단 배너** (서버에서 읽은 현재 상태 기준)

| 매장 | 진입 | 상단 배너 | 저장 버튼 |
|---|---|---|---|
| 개인 · `approved` | OW1 `핵심 정보 수정…` | info 「아래 정보는 관리자 검토 후 반영돼요.」(앱 문구) | `검토 요청 보내기…` |

| **브랜드 가맹** (모든 상태) | **이 라우트로 진입하면** `#/o/store` 로 되돌린다 | — | — |

**주소 필드 (U1)**: 기본안은 **읽기 전용 표시 + 안내**. 주소를 바꾸려면 좌표 변환이 필요한데 웹에서 시크릿 없이 안전하게 처리할 근거가 없다(절대규칙 4). 사용자가 U1 에서 (B) 를 택하면 `[주소 찾기]` 버튼(우편번호 검색 → 좌표 변환 성공 시에만 주소·좌표를 한 쌍으로 갱신, 실패 시 「좌표 변환에 실패했어요. 다른 주소로 다시 시도해주세요」 앱 문구, 주소만 바뀌고 좌표가 안 바뀌는 상태 금지)로 바꾼다.

**검증**: 필수 필드 trim 후 1자 이상. 사업자등록번호는 앱과 같은 형식 검증(DV-13). 카테고리는 최소 1개(앱 규칙 확인 DV-13). 「필수 항목을 모두 입력해주세요」(앱 문구)는 저장 시도 시 상단 요약 대신 **필드별 오류**로 표시한다.

**`rejected` 재제출 모드에서도 UI 는 `approvedAt` 에 대해 아무것도 보여주거나 묻지 않는다.** 재제출 payload 의 승인 메타 정리는 서버 현재 상태가 `rejected` 일 때만 붙는 **내부 동작**이다(§16 DV-5). 사용자에게 이 필드를 노출하는 컨트롤·문구가 없다.

| 갈래 | 서버 현재 상태 | 안내 문구 (본문 하단 블록, `.a-banner` info) |
|---|---|---|
| **A** | `approved` 또는 (`pending` + `approvedAt != null`) | 「상호명 · 주소 · 사업자등록번호를 바꾸면 관리자 재승인 대상이 됩니다. **영업과 주문은 그대로 계속됩니다.**」 + 메뉴 카테고리가 바뀌는 경우에만 한 줄 추가: 「메뉴 카테고리를 바꿔도 같은 재승인 대상이에요.」 |
| **B** | `pending` + `approvedAt == null` | 「아직 첫 승인을 기다리는 매장이에요. 수정한 내용으로 다시 검토해요. 승인되기 전에는 주문을 받을 수 없어요.」 (**「계속됩니다」 문구 금지**) |
| **C** | `rejected` | 「재제출하면 관리자가 다시 검토해요. 승인되기 전에는 주문을 받을 수 없어요.」 |

- 모달 제목/버튼 라벨: 갈래 A·B `핵심 정보 변경 검토 요청` / `검토 요청 보내기`, 갈래 C `매장 재제출` / `재제출하기`.
- 초기 포커스: **취소 버튼**(승계: Enter 한 번에 확정 안 되게).
- **재읽기 결과가 모달을 연 시점의 가정과 다르면**(예: 화면은 `approved` 였는데 서버는 이미 `rejected`/`pending`, 혹은 admin 이 그 사이 승인) 쓰지 않는다. 모달 본문을 새 갈래 문구로 **교체**하고 info 한 줄 「매장 상태가 바뀌었어요. 안내를 확인하고 다시 눌러주세요.」 + 확정 버튼은 사용자가 다시 눌러야 한다(자동 진행 금지).
- 재읽기 실패: 「매장 상태를 확인하지 못했어요」 error 배너 + 확정 disabled + `[다시 확인]`. 확인 없이 쓰지 않는다.

**성공 후** (낙관 금지, 서버 응답 후): 모달 닫기 → `#/o/store` 이동 → 서버 재조회 → 토스트
- 갈래 A: 「검토 요청을 보냈어요. 검토 동안 매장은 계속 노출됩니다」(앱 문구)
- 갈래 B: 「검토 요청을 보냈어요」(앱 문구)
- 갈래 C: 「재제출이 완료되었어요」(앱 문구)
- 재조회 실패 시: 승계 문구 「요청은 저장되었지만 화면을 새로 고치지 못했어요. 새로고침을 눌러주세요.」 warn 배너 (쓰기 성공 응답을 받았으므로 사실)

**실패 후**: 승계(admin §6-5) — 모달 유지, 입력 보존, 배너 「저장되지 않았어요…」, 불확실한 결과(응답 유실)는 「상태 확인하기」. 문구는 admin §8 쓰기 오류 표를 쓰되 「항목은 아직 대기 중이에요」 를 「**변경 내용은 아직 반영되지 않았어요**」 로 바꾼다(이 쓰기는 큐 항목이 아니다).

|---|---|---|---|
| 폼 화면 | 폼 카드 스켈레톤 | 중앙 오류 블록 | 매장 없음 GT3 |

### BR4. 검토 현황 `#/b/tracking`

내가 제출한 **마스터 메뉴 · 가격 오버라이드 · 점포 한정 메뉴** 중 대기·반려 건을 한곳에서 본다. 처리 버튼 없음(읽기). 앱의 비정합 ⓑ를 복제하지 않는다.

```
 h1 검토 현황  [읽기]                                      마지막 갱신 14:02 [새로고침]
 [전체] [대기] [반려]                                                  총 N건
 ┌──────────────────────────────────────────────────────────────────────────┐
 │ 구분            대상                       상태       제출         │        │
 ├──────────────────────────────────────────────────────────────────────────┤
 │ 마스터 메뉴     아메리카노                 ● 대기     3시간 전    열기 →    │
 │ 가격 오버라이드 아메리카노 · 강남점 · ₩4,000 ● 반려됨  2일 전     열기 →    │
 │   └ 반려 사유: 가격이 너무 낮아요 (펼침)                                    │
 └──────────────────────────────────────────────────────────────────────────┘
```

- 구분 열 라벨은 앱 그대로: 「마스터 메뉴」 「가격 오버라이드」 「점포 한정 메뉴」(앱에서는 「매장」 「메뉴」 「가격」 으로 축약돼 있음 — 웹은 풀 이름). 시간은 앱 상대 표기(「방금 전」 「N분 전」 「N시간 전」 「N일 전」) + `title` 에 절대 시각.
- `열기 →` 는 출처 화면(BR6 / BR13 해당 행 / BR14)으로. 반려 건의 사유는 행 아래 펼침(기본 접힘).
- 데이터가 **산하 매장 N개를 차례로 조회**해야 모인다(인덱스 부재 — spec R-B11). 따라서:

| 상태 | 표시 |
|---|---|
| **loading** | 헤드 + 필터 활성 + 표 스켈레톤 6행. 조회가 길어지면 표 위에 3px 로딩바 + 「산하 매장 3 / 12곳 확인 중…」(13px muted). 이미 모인 행은 **도착하는 대로 추가**하되 표 아래에 「확인 중」 표식 유지 |
| **error** (전부 실패) | 오류 블록 + `[다시 시도]` |
| **부분 실패** (일부 매장만) | 모인 행은 보여주되 표 위 **warn 배너 「일부 매장의 항목을 불러오지 못했어요 (N곳). 아래 목록은 전부가 아닐 수 있어요.」 + `[실패한 곳만 다시 시도]`.** 부분 목록을 완전한 것처럼 보이지 않게 하는 것이 핵심 |
| **empty** | 「제출한 항목이 없어요」 / 「매장 또는 가격 재정의를 제출하면 여기에서 검토 상태를 확인할 수 있어요.」(앱 문구). 모든 조회 성공 + 0건일 때만. 필터 결과 없음은 다른 문구 + 「필터 지우기」 |

### BR5. 마스터 메뉴 목록 `#/b/menus` · BR6 상세 `#/b/menus/{id}`

- 상태 배지: 승인됨 / 대기 / 반려됨 + `approvedAt` 이 있는 대기 건은 글자 **「수정 대기」**(spec W-B5: 승인 이력이 남은 대기). 색이 아니라 글자로 구분(승계).
- 이름 링크 → BR6. 행 끝 `⋯` 대신 텍스트 링크 3개를 노출한다(메뉴 아이콘 없이): `편집` `복제` `삭제…`. `편집` 은 BR8(핵심) 로 가고, 운영 항목은 BR6 에서 `운영 정보 수정` 으로.
- **노출 스위치**는 운영 수정 경로(W-B6 5키)로 즉시 반영(N3). 승인 전 메뉴도 스위치는 동작한다 — 상태 배지로 사실 구분.

## 11. customer 섹션 — 비어 있는 정식 섹션

### 11-1. 설계 의도

고객이 오면 「앱을 쓰세요」 로 돌려보내지 않는다. **오래 머물 공간의 첫 입주 3화면**이다. 그래서:

- 네비가 다른 역할과 **같은 모양**(같은 사이드바, 같은 항목 높이, 같은 헤드)이다. 「고객 전용 간이 화면」 처럼 보이지 않게 한다.
- **자동 로그아웃 없음.** 공용 PC 방치는 사이드바의 명시적 `로그아웃` 과 Auth 기본 세션 만료로 다룬다.
- 「아직 없음」 은 **네비의 비활성 항목이 아니라 본문 안의 준비 중 카드**로 말한다(비활성 메뉴 금지, spec §10.1).
- 읽기 전용(Q6). 이름 변경 등 쓰기 컨트롤을 두지 않는다. 읽기 화면 헤드마다 `읽기` 칩 대신 그룹 라벨 옆 칩 하나(§3-2).

### 11-2. 준비 중 카드 (N11) — 「향후 확장 지점」 의 시각 약속

| 항목 | 명세 |
|---|---|
| 모양 | 카드 안쪽 패딩 20px, 배경 `--surface`, 테두리 `1px dashed var(--border)`, 라운드 `--radius`. 제목 16px/700 `--text-heading` + 우상단 칩 「준비 중」(`.a-chip`). 본문 14px `--text-body` |
| **하지 않는 것** | 링크·버튼·호버·포커스·클릭 가능해 보이는 그림자, 「알림 받기」「출시일」 약속, 진행률 표시, 자물쇠 아이콘, 비활성 회색 버튼 |

**승격 규칙 (확장 지점)** — 기능이 생길 때 바뀌는 곳은 **정해진 두 군데뿐**이다:

| **리뷰** | CU1 의 「리뷰」 준비 중 카드 **삭제** + 네비 「내 정보」 그룹에 항목 「내 리뷰」 `#/u/reviews` **추가** + 뷰 1개 | Rules·CF 이미 있음. 작성은 주문 자격·`serverTimestamp()`·14일 기한(UI 강제)이 필요 |
| **게시글** | 동일 (`#/u/posts`) | 컬렉션·Rules 부재 → 별 과제 T1 선행 |
| **QnA** | 동일 (`#/u/qna`) | 동일 |
| 즐겨찾기 | 준비 중 카드 없이 바로 네비 항목 추가 가능 | Rules 있음, 1차 미노출 |

셸·네비 골격·에러 분류·확인 모달·payload 가드는 다시 만지지 않는다 — **「카드 1장 삭제 + 네비 1줄 + 뷰 1개」** 가 승격의 전부다.

| 영역 | loading | error | empty |
|---|---|---|---|
| 프로필 카드 | 아바타·행 스켈레톤 | 카드 내 오류 「프로필을 불러오지 못했어요」 + `[다시 시도]` (권한 거부 → G5) | 문서 부재: 값 `-` + 캡션 §5-5 (오류 아님) |
| Qoin 카드 | 값 스켈레톤 | 카드 내 오류 | 「Qoin 정보가 아직 없어요」 |
| 준비 중 3카드 | 해당 없음(정적) | 해당 없음 | 해당 없음 |

### CU2. 주문 내역 (Log) `#/u/log`

용어: 헤드 「**주문 내역 (Log)**」, 사이드바 「주문 내역 (Log)」. 본문 안에서는 짧게 「Log」 로 칭한다.

```
 h1 주문 내역 (Log)                                        마지막 갱신 14:02 [새로고침]
 지금까지 Qradar 에 남긴 주문 기록이에요.                                    (13px muted)
 ┌──────────────────────────────────────────────────────────────────────────┐
 │ 주문 일시         매장              주문 내용             금액      상태   │
 ├──────────────────────────────────────────────────────────────────────────┤
 │ 2026-10-28 13:58  모카하우스 강남점  아메리카노 외 1건     9,500원  ● 완료  │
 └──────────────────────────────────────────────────────────────────────────┘
 총 N건                                   [더 보기]  (25건씩)
```

- 열 구성은 `orderLogs` 의 실제 필드를 확인해 매핑한다(DV-15); 없는 필드의 열은 뺀다. 최신순. 행은 링크 아님(상세·재주문·환불 없음 — spec 비범위 N13).
- 상태 배지는 OW4 매핑과 동일(글자 + 점).

| 상태 | 표시 |
|---|---|
| loading | 표 스켈레톤 8행 |
| error | 오류 블록 + `[다시 시도]`. 더 보기 실패 시 표는 유지하고 표 아래 오류 한 줄 |
| empty | 「아직 남긴 Log 가 없어요」 / 「주문을 하면 Qradar 가 Log 로 남겨요」 |

### CU3. Qoin `#/u/qoin`

```
 h1 Qoin                                                   마지막 갱신 14:02 [새로고침]
 ┌ 보유 Qoin ──────────────┐
 │ ● 12,400                │   <- 34px/800 (CU1 과 같은 값 출처)
 └──────────────────────────┘
 거래 내역                                                              (h2 18px)
 ┌──────────────────────────────────────────────────────────────────────────┐
 │ 일시              구분        Qoin      관련 주문                         │
 │ 2026-10-28 14:02  적립        +400       모카하우스 강남점                  │
 └──────────────────────────────────────────────────────────────────────────┘
```

- 거래 원장은 **append-only 로 서버만 쓴다**(CF 전담): 어떤 편집·삭제 컨트롤도 없다. 열은 `qoinTransactions` 실제 필드로 확정(DV-15). 구분 라벨은 원장의 type 값을 한국어로 매핑하되 **모르는 값은 원문 표시**.
- Qoin 사용·교환·선물은 미구현이므로 관련 문구·버튼 없음.

| 상태 | 표시 |
|---|---|
| loading | 보유 카드 + 표 스켈레톤 |
| error | 보유 카드와 거래 표가 **서로 독립** 오류 |
| empty | 보유: 0 은 사실이면 `0 Q`(문서가 있고 값이 0 일 때만), 값이 없으면 「Qoin 정보가 아직 없어요」. 거래: 「아직 Qoin 거래가 없어요」 / 「주문이 완료되면 Qoin 이 적립돼요」 |

## 12. 쓰기 인터랙션 공통 (admin §6 확장)

### 12-1. 쓰기 유형별 확인 단계

| 유형 | 예 | 확인 단계 | 성공 후 | 실패 시 |
|---|---|---|---|---|
| **즉시 반영 폼** | OW2, BR2, BR9, OW7(개인 매장), 서브 카테고리·옵션 그룹 저장 | 없음 (대상 이름은 저장 바/모달 제목에) | 토스트 + 서버 재조회로 화면 갱신 | 저장 바 위 영구 error 배너, **입력 보존** |
| **즉시 반영 스위치** | 노출·품절·활성 | 없음 | 응답 후 스위치 상태 갱신 | 상태 불변 + 행 아래 오류 |
| **재승인·검토 요청** | OW3, BR3, BR7, BR8, BR13 행 제출, BR14 | **변경 확인 모달** (§6-1) + 서버 재읽기 | 모달 닫기 → 이동 → 서버 재조회 → 토스트 | 모달 유지, 입력 보존 |
| **삭제** | 메뉴·카테고리·옵션 그룹 | **삭제 모달** | 목록 서버 재조회 → 토스트 「삭제됐어요」 | 모달 유지 |
| **연결(claim)** | GT1 | 버튼 한 번 + 결과 서버 재읽기 | 셸 재구성 | 배너 |

### 12-2. 낙관적 UI 금지 — 화면별 체크

- 스위치: 눌러도 상태가 바뀌지 않는다. 응답 후에만.
- 목록: 쓰기 후 로컬에서 행을 지우거나 배지를 바꾸지 않는다. **서버 재조회**로 다시 그린다. 재조회 실패 시 「요청은 저장되었지만 화면을 새로 고치지 못했어요…」(승계).
- 건수·상태 배지·사이드바 컨텍스트 블록의 상태 배지도 재조회 결과로만 바뀐다.
- **불확실한 결과**(응답 유실·타임아웃): 성공/실패 단정 금지. 「응답을 확인하지 못했어요. 처리됐는지 확실하지 않아요.」 + `[상태 확인하기]`(해당 문서 서버 재읽기) — 그 전까지 같은 쓰기 버튼 disabled. 문구와 동작은 admin §6-5 승계.
- 역할이 바뀌어 쓰기가 거부되면 성공으로 보이지 않는다(§5-6).

### 12-3. 폼 공통

| 항목 | 명세 |
|---|---|
| 변경 감지 | 초기값(서버에서 읽은 값)과 비교해 바뀐 필드만 dirty. 되돌려서 같아지면 dirty 해제 |
| 저장 안 한 이동 | N15. 라우트 전환·뒤로가기·탭 닫기 |
| 입력 보존 | 실패 시 입력값 전부 유지. 성공 후에만 초기값 갱신 |
| 서버 값이 그 사이 바뀜 | 저장 직전 재읽기가 필요한 쓰기(§9-3)만 확인. 즉시 반영 폼은 **바뀐 필드만** 보내 충돌 면적을 줄인다(DV-12) |
| 포커스 | 페이지 진입 시 `h1` 로 포커스 이동(`tabindex=-1`), 저장 실패 시 error 배너로 |
| 키보드 | 폼 안 `Enter` 로 저장하지 않는다(textarea 줄바꿈 충돌·오제출 방지). 저장 버튼 명시 클릭 |

### 12-4. 금지 UI (재확인)

역할 부여/변경 · brand 의 자기 제출물 승인/반려 · owner 주문 접수·제조·완료·환불 거절 · Qoin 적립률·비상 정지 편집 · 매장 삭제 · 브랜드 신규 등록 · 고객 프로필 수정 · 브랜드 키 발급/재발급. 이 중 어느 것도 **비활성 버튼 형태로도** 두지 않는다(보이지만 못 누르는 버튼 = 곧 기능이 있다는 약속).

## 13. 오류 문구 추가분 (admin §8 표에 더함)

admin §8 의 읽기·쓰기 표를 그대로 쓴다. 역할별 콘솔에서 **추가**되는 것만:

| 상황 | 제목 | 설명 | 비고 |
|---|---|---|---|
| 역할 재확인 실패 | 불러오지 못했어요 | 권한을 다시 확인하지 못했어요. 연결을 확인한 뒤 다시 시도해주세요. | §5-6 |
| 역할 변경 | (배너) 권한이 바뀌었어요. 화면을 다시 구성했어요. | | §5-6 |
| 쿼리에 필수 조건 누락(구현 버그) | 불러오지 못했어요 | 잠시 후 다시 시도해주세요. | 사용자에겐 일반 문구, 원인(`where storeId==` 누락 등)은 콘솔 로그. 화면에 Rules·쿼리 원문 노출 금지 |
| 쓰기: 화이트리스트 위반(구현 버그) | 저장되지 않았어요 | 잠시 후 다시 시도해주세요. | 동일. tester 가 이 오류가 **사용자 경로에서 발생하지 않음**을 검증 |
| 사진 5MB 초과 | (필드 오류) | 이미지 용량이 5MB를 초과했습니다. (x.xMB) | 앱 문구 |
| 이름 중복 | (필드 오류) | 이미 같은 이름의 분류가 있어요 / 이미 같은 이름의 옵션 그룹이 있어요 | 앱 문구 |
| 사용 중 삭제 시도 | (모달) | N개 메뉴에서 사용 중이라 삭제할 수 없어요 | 신규 문구 |
| 연결(claim) 실패 | §7-1 표 | | `details.reason` 별 |
| 매장 상태가 바뀜(핵심 수정 확인 중) | (모달 info) | 매장 상태가 바뀌었어요. 안내를 확인하고 다시 눌러주세요. | §9-3 |
| 일부 매장 조회 실패(검토 현황) | (warn 배너) | 일부 매장의 항목을 불러오지 못했어요 (N곳). 아래 목록은 전부가 아닐 수 있어요. | BR4 |
| 삭제 중간 실패(cascade) | (모달 error) | 일부 가격 오버라이드만 삭제하고 멈췄어요. 메뉴는 아직 남아 있어요. 다시 시도하면 이어서 삭제돼요. | BR6 |

**문구 규칙 보강** (admin §9 승계 + 추가)
- 「차단」 「제한」 「접근할 수 없어요」 로 **UI 가 권한을 집행한다는 인상** 금지. 사실만: 「~할 수 없어요」, 「~은 앱에서 해요」.
- 「숨겼어요」 「보이지 않게 했어요」 를 보안 설명으로 쓰지 않는다. (손님에게 안 보인다는 **서비스 동작**을 설명하는 앱 문구 「손님에게 숨김」 은 보안 얘기가 아니므로 허용)
- 재승인 문구에는 「영업이 중단돼요」 **금지**(사실이 아님), 「계속된다」 는 §9-3 갈래 A 에서만.
- 응답 전 완료형 금지(승계): 「저장했어요」 는 응답 이후에만.

## 16. developer 전달 특이사항

- **DV-1 (보안 문구)** admin DV-1 승계. 코드 주석·UI 어디에도 「메뉴를 숨겨서 안전」 류 서술 금지. 네비 축소·해시 정규화·버튼 미렌더는 혼동 방지일 뿐이고 권위는 Rules/CF.
- **DV-2 (셸 렌더 시점)** admin DV-2 승계. 역할 판정 성공 전에는 사이드바·본문 DOM 을 만들지 않고 데이터 요청도 없다. 판정 성공 후에도 **다른 역할 섹션 코드는 동적 `import()` 로 불러오지 않는다**(spec §8.1).
- **DV-3 (역할 판정 반환 형태)** `readUserRole` 이 `{admin:boolean}` 이라 「문서 부재」 와 「비admin」 이 구분되지 않는다. `{ exists, role, brandId }` 로 확장하고 분류:
  `getDoc` **성공** → `!exists` ⇒ `customer` / `exists` 이고 `role` 필드 **부재(undefined)** ⇒ `customer` / `role ∈ 4종` ⇒ 해당 역할 / **그 외 present 값(null·빈 문자열·숫자·미정의 문자열)** ⇒ G3. `getDoc` **실패·타임아웃·데이터가 객체 아님** ⇒ G2. 이 분기를 한 함수에 모아 단위 테스트 가능한 순수 함수(SDK 없음, `console-format.js`)로 둔다.
- **DV-4 (역할 변경 재확인)** `permission-denied`(읽기·쓰기)를 한 곳에서 가로채 `recheckRole()` 호출. **단일 비행**(진행 중이면 같은 Promise 공유) + 완료 후 3초 안의 재호출은 직전 결과 재사용. 폴링·`onSnapshot` 구독 금지. 비교 대상은 `role` 과 `brandId`.
- **DV-5 (🔴 `approvedAt`)** `approvedAt` 을 입력받거나 보여주거나 **수정하는 UI 는 없다.** `rejected` 매장의 재제출 payload 만 승인 메타를 null 클리어하며, **그 분기는 확인 모달 직후 서버 재읽기로 `status==='rejected'` 를 확인한 경우에만** 만든다. 화면의 낡은 상태로 `isResubmit` 를 정하지 않는다(승인 매장에서 그 경로를 타면 그 순간 `canSellNow` 가 false). 서버 상태가 `approved`/`pending` 이면 payload 에 `approvedBy` `approvedAt` `rejectedAt` `rejectedReason` 키를 **넣지 않는다.** 가능하면 트랜잭션으로 「읽기 → 상태 확인 → 쓰기」를 묶는다(admin DV-4 승계). `console-payloads.js` 에 「운영 폼 payload 에 핵심 키 금지 / 핵심 폼 payload 에 운영 키 금지 / 비-rejected 에 승인 메타 금지」 가드 추가.
- **DV-6 (두 폼 분리)** OW2 와 OW3 는 **라우트·DOM·payload 빌더가 모두 분리**. 하나의 `saveStore(fields)` 함수로 합치지 않는다.
- **DV-7 (낙관적 UI 금지)** admin DV-3 승계 + 스위치/행 제출/삭제까지 확대(§12-2).
- **DV-8 (CSS)** admin DV-8 승계. `console.css` 는 `style.css` 변수만 상속. 신규 hex 0. 파생색 `color-mix` + 변수. N1~N15 의 색은 §2 표만 사용. `.a-` 접두 유지.
- **DV-9 (brand 연결 UI)** `brand_id_missing_view.dart` 의 분기·문구를 원본으로 삼는다(제출 브랜드 0/1/N건, 선택 규칙, 결과 문구). 위 §7-1 은 그 요약이며 앱이 다르면 앱을 따른다.
- **DV-10 (읽기 화면 필드)** OW5 `reviews`, OW4 주문 열, CU2 `orderLogs`, CU3 `qoinTransactions` 의 **열은 실제 필드를 확인해 맞추고 없는 열은 뺀다**(admin DV-6 과 같은 방식). 평균 점수 표기(`grade_min_reviews` 의 「신규」 규칙)는 **작업 중인 다른 세션의 `lib/` 최신 구현**을 확인해 일치시킨다.
- **DV-11 (메뉴 폼 필드)** 핵심/운영 분류와 필드 목록은 앱의 메뉴 폼·판정 함수가 단일 진실원. §10 BR6 표는 spec 기준 기본안. `createdAt` 은 수정 payload 에 넣지 않는다(spec W-O2). 오버라이드 create 에 `masterMenuItemId` 포함(Q2). 마스터 운영 수정에 `disabledOption*` 포함(Q4).
- **DV-12 (운영 폼 payload)** OW2 는 **바뀐 필드만** + `updatedAt`. 카테고리 섹션 로드 실패 시 `excludedMainCategories` 는 보내지 않는다. 휴면 제외 코드 보존. `businessHours` 비움 = 필드 삭제. `imageUrl` 은 `imageUrls` 변경 시에만 동반.
- **DV-13 (핵심 폼 검증)** 사업자등록번호·카테고리 최소 개수·매장명 규칙은 `store_core_form_page.dart` 와 동일하게. 브랜드 가맹 매장은 OW3 라우트 진입 시 `#/o/store` 로 되돌림.
- **DV-14 (브랜드 운영 수정)** BR2 는 `brands/{id}` 와 `private/profile` 두 문서를 **한 배치**로 쓴다(한쪽만 저장되는 상태 방지). payload 는 spec W-B1/W-B2 의 허용 키 부분집합만, **브랜드 핵심 수정(BR3)에도 `brandKey` `approvedBy` `approvedAt` `createdAt` 을 넣지 않는다**(W-B1 경고).
- **DV-15 (표 열)** 위 DV-10 과 같은 원칙. 모르는 enum 값은 원문 표시.
- **DV-16 (매출)** `getDocsFromServer` 서버 강제(캐시 금지 — 0원이 정상으로 보이는 사고 방지), `where storeId==` 필수, 1,000건 절단 표시, 집계는 앱 `aggregateStoreSales` 와 동일. 기간 계산은 KST 반열린 구간.
- **DV-17 (검토 현황)** 인덱스를 추가할 수 없으므로 산하 매장별 서브컬렉션 N회 조회. **부분 실패를 전체 성공으로 합치지 않는다**(BR4 warn 배너).
- **DV-18 (삭제 cascade)** 마스터 메뉴 삭제는 오버라이드 선삭제 → 메뉴 삭제 순서, 사전 영향 조회 필수, 중간 실패 재시도 가능. Rules 접근 예산(spec W-B8)을 지켜 청크 처리.
- **DV-19 (네비 구성)** `NAV` 상수를 역할별 맵으로. 개인 매장 전용 2항목은 매장 유형 확정 후 마지막에 추가. 전제 미충족 시 축소 네비(§3-4). 전제 해소 후 재구성. `S.counts`/`loadAllCounts` 는 **admin 일 때만** 시작.
- **DV-20 (customer 확장성)** `section-customer` 의 뷰는 **테이블 주도 등록**(해시 → 뷰 함수 + 네비 라벨). 준비 중 카드도 데이터 배열. 승격 = 배열에서 카드 삭제 + 네비 배열에 한 줄 + 뷰 등록(§11-2).
- **DV-21 (불필요한 자동 로그아웃 제거)** `renderNotAdmin` 을 G3(모르는 role) 전용으로 축소하고 문구를 §5-4 로 교체. 비admin 계정이 정상 셸로 가는 경로에서 `signOutNow` 가 호출되지 않는지 확인.
- **DV-22 (`index.html`)** `<title>` 「Qradar 콘솔」, 주석의 `/admin/index.html` 표기 정정. 랜딩 링크 추가 금지(확정 2).
- **DV-23 (접근성)** admin DV-9 승계 + 스위치 `role="switch"`·글자 병기, 탭/표 키보드 이동, 모달 포커스 트랩, 상태 변화 `aria-live`, `prefers-reduced-motion`.
- **DV-24 (복사 버튼)** admin DV-13 승계(브랜드 키·UID 복사 실패 시 「복사하지 못했어요」).
