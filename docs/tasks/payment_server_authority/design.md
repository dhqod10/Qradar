## 0. 이 설계의 한 줄

> 서버가 결제를 거절할 수 있게 되면서 **고객 앞에 처음 생기는 실패**를, 고객이 **스스로 복구할 수 있는 문장과 버튼**으로 바꾼다.
> 오탐(정상 손님이 막히는 경우)이 있을 수 있으므로 모든 거절 화면은 **(1) 무엇이 문제인지 지목하고 (2) 돈이 안 나갔음을 말하고 (3) 다음 한 걸음을 버튼으로** 준다.

## 1. 설계 판단 (근거 포함)

### D1. 선검증 UI 는 "막는 장치"가 아니라 "미리 알려 주는 장치"다 (Q4)

선검증의 실패 방향은 서버 게이트와 **반대**다. 선검증이 네트워크 실패하면 **결제를 막지 않는다** (spec §8.2).
이 때문에 UI 에 아래 규칙이 붙는다.

| 규칙 | 내용 | 이유 |
|---|---|---|
| **N1. 긍정 표시 금지** | "재고 확인됨", "주문 가능", 초록 체크, "확인 완료" 같은 **통과를 알리는 표시를 어디에도 두지 않는다.** 통과는 "아무 표시 없음" 이다 | 선검증이 조용히 실패한 상태와 통과한 상태는 화면에서 **구분되면 안 된다.** 구분하는 순간 "확인됨" 이라는 거짓 확신을 만든다 |
| **N2. 타입에 "확인됨" 을 만들지 않는다** | 카트 행의 상태 enum 에 `verified` / `ok` 값을 **두지 않는다.** `normal`(= 모름 또는 문제 없음) 하나뿐이다 | UI 가 "확인됨" 을 그릴 수 있는 길 자체를 없앤다. developer 는 이 enum 에 값을 추가하지 않는다 |
| **N3. 자동 실패는 무음, 사용자가 직접 누른 확인의 실패는 정직하게** | 자동 선검증이 실패하면 아무것도 보이지 않고 결제가 진행된다. 단 고객이 **"다시 확인" 을 눌렀는데 실패**하면 "확인하지 못했어요" 를 알린다 | 자동 검증의 무음은 N1 때문이다. 사용자가 질문(다시 확인)을 던졌는데 대답을 안 하는 것은 거짓말이 아니라 먹통이다. 이 경우 "확인 못 함" 은 "통과" 가 아니므로 N1 을 어기지 않는다 |
| **N4. 선검증 타임아웃** | 선검증은 **3초**를 넘기면 포기하고 결제를 진행한다. 이 동안 결제 버튼은 기존 `_processing` 스피너 (통과 시와 동일한 모양) | 느린 네트워크가 정상 손님의 결제를 지연시키지 않게 한다. 스피너가 길어지는 것 외에는 통과/무음 실패가 구분되지 않는다. 3초는 추천값이며 Q6 |
| **N5. 선검증 "양성"(위반 발견)은 서버 신선 읽기에서만** | 위반을 보여 주는 근거는 이번 탭에서 새로 읽은 값이다. 오래된 스트림 캐시 하나로 결제를 막지 않는다 | 클라이언트 오탐으로 정상 손님이 막히는 것은 서버 오탐과 똑같이 "돈이 멈추는 방향" 이다 |
| **N6. 막혀도 막다른 길이 없다** | 위반 안내에는 항상 (a) 해당 품목 빼기 (b) 다시 확인 (c) 카트 확인 중 하나 이상의 동작이 붙는다. 영구적으로 비활성인 결제 버튼은 만들지 않는다 | 선검증이 틀렸거나 점주가 막 품절을 풀었을 때 고객이 빠져나올 길이 있어야 한다 |

### D2. 모든 거절 문구는 "지목 + 돈 + 다음 행동" 3요소

1. **지목**: 무엇이 문제인가 (매장 / 메뉴 이름).
2. **돈**: 요금이 나갔는가. 서버 게이트 거절은 Toss confirm **전**이므로 "아직 결제되지 않았고 요금도 청구되지 않았어요" 를 말해 준다. 고객은 카드 승인창을 끝까지 통과한 뒤에 이 화면을 보므로 "빠져나갔나?" 가 첫 번째 걱정이다.
3. **다음 행동**: 문장 끝이 "~할 수 없습니다" 로 끝나지 않는다. 버튼이 곧 다음 행동이다.

**돈에 대한 주장은 사유 토큰을 아는 경우에만 한다** (D3). 모르는 실패에는 "요금이 안 나갔다" 고 말하지 않는다. 그 실패는 Toss confirm 이후일 수 있다.

### D3. 실패의 세 갈래 — 돈의 상태가 다르면 문구와 버튼이 달라야 한다

현재 `payment_result_page.dart` 는 세 가지를 한 화면으로 처리한다. 돈 상태가 다르므로 분리한다.

| 갈래 | 발생 지점 | 돈 상태 | 판별 방법 | 화면 |
|---|---|---|---|---|
| **A. 결제창 단계 실패** | `launchPayment` 가 `success:false` + Toss `errorCode` (`checkout_page.dart:84-94`) | 안 나감 | `errorCode != null` | 기존 매핑 유지 + **기본 문구에서 원문 제거** (§3.2) |
| **B. 서버 게이트 거절** | `verifyTossPayment` 가 `[REASON]` 토큰 포함 오류 (`checkout_page.dart:126-135`) | **안 나감** (confirm 전, spec R5) | 토큰이 **알려진 6개 사유** | 사유별 화면 (§3.1) |
| **C. 확인 단계의 알 수 없는 실패** | `verifyTossPayment` 호출이 토큰 없이 실패 (네트워크 끊김·타임아웃·알 수 없는 사유 포함) | **모른다** (confirm 이후일 수 있다) | 토큰 없음 또는 모르는 토큰 | "주문 확인이 필요해요" 화면 (§3.3) — **요금 청구 여부를 단정하지 않고 Log 확인을 첫 행동으로** 준다 |

C 가 중요한 이유: 지금의 `e.toString()` 기본 폴백은 C 에 속하는 실패(주문 생성 도중 끊김)에서 고객에게 원문을 보여 준다. 원문을 지우면서 "다시 시도" 만 남기면 **이미 결제된 고객이 다시 결제**할 수 있다. 그래서 C 의 첫 행동은 "다시 시도" 가 아니라 **"Log 에서 확인"** 이다.

### D4. 모르는 사유 코드가 와도 원문이 새지 않는다

- 화면에 그리는 문자열은 **오직 코드 안의 상수 문구**다. 서버가 보낸 `message` / `e.toString()` / Toss `errorMessage` 를 화면 텍스트에 **보간하지 않는다.**
- 매핑 테이블에 없는 토큰·코드 → **갈래 C 의 기본 문구** (또는 갈래 A 면 A 의 기본 문구).
- 새 사유가 서버에 추가되면 **앱 업데이트 전까지는 C 화면으로 떨어진다.** 이것은 의도된 안전 방향이다 (돈을 안 나갔다고 잘못 말하느니 확인을 시킨다). 새 사유를 추가하는 사람은 §3.1 표에 행을 추가한다.
- 문의 코드 캡션 (`오류 코드: XXX`) 은 **토큰이 `^[A-Z][A-Z0-9_]{2,39}$` 형식일 때만**, 그리고 **갈래 C 와 갈래 A 의 기본 문구 화면에서만** 작게 보인다. 원문이 아니라 식별자이므로 새지 않는다. 노출 여부는 Q2.

### D5. 품절 거절은 메뉴 이름을 반드시 지목하고, **전부 열거**한다

- 이름이 오탐일 때 고객의 **유일한 복구 수단**이다.
- 표시 방식: **N개 + 더보기로 줄이지 않고 전부 열거한다.** 근거: ① 카트는 1매장 단위라 품목이 대개 한 자릿수다. ② 줄이면 "빼야 할 메뉴" 가 숨어서 복구가 한 단계 늘어난다. ③ 줄이는 이득(세로 공간)이 열거 못 하는 손실보다 작다. ④ 화면 본문을 **스크롤 가능**하게 만들고 버튼을 하단 고정하면 개수가 많아도 깨지지 않는다.
- 중복 제거: 같은 `menuItemId` 가 옵션이 달라 여러 줄이면 **이름을 한 번만** 보인다.
- **이름은 서버가 보낸 문자열이 아니라 고객 카트의 `menuItemName` 으로 그린다.** 서버 토큰에는 `menuItemId` 만 싣는다 (§7 전달 사항 1). 이유: 고객이 카트에서 보던 이름과 같아야 알아본다. 토큰에 한글 이름·쉼표를 싣는 인코딩 문제가 없다. `details` 가 안 올라오는 실기기 문제 (`backlog.md:566-569`) 에도 토큰만으로 버틴다.
- id 가 카트에서 해석되지 않으면 (카트가 그 사이 바뀜) 그 id 는 건너뛴다. **전부 해석 실패하면** 이름 없는 문구 ("품절된 메뉴가 있어요") 로 내려가고 버튼은 같다 (spec §12 사실 2 의 ⓑ 행).

### D6. 서버가 지목한 메뉴는 카트에도 표시된다 (결제 화면과 카트의 말이 같아야 한다)

결제 실패 화면은 "A 메뉴가 품절" 이라 하는데 카트로 돌아가 보니 A 행에 아무 표시가 없으면 고객은 "버그" 라고 판단한다. 서버가 지목했는데 클라이언트 선검증은 통과하는 경우 (스트림 캐시 지연, 클라이언트 오탐 없음) 가 실제로 생긴다.

- 서버 거절이 지목한 `menuItemId` 를 **메모리에만 보관** (`paymentRejectedMenuIdsProvider`, 앱 재시작·카트 비우기·해당 줄 삭제 시 소거).
- 카트 행은 그 id 에 대해 `rejectedByServer` 상태를 그린다 (§4.1). 결제를 **막지는 않는다** (N6). 고객이 "다시 확인" 에서 클라이언트 신선 읽기가 정상으로 나오면 메모리 플래그를 지운다.

### D7. 사실 하나에는 판정 함수 하나 (표면 인벤토리 §2)

화면은 `canSellNow` / `applyOverrideForCustomer` 결과만 렌더하고 `soldOut` / `status` 를 직접 비교하지 않는다. 이 설계가 추가하는 표면 (카트 행, 카트 배너, 빠른 재주문, 결제 시트) 은 모두 `ValidateCheckoutUseCase` 한 곳의 결과를 소비한다.

## 2. 표면 인벤토리 (spec §12 이전 + 확장)

> 규칙: ⓑ 가 빈 칸이면 미설계다. 행을 추가하지 않고 화면을 만들면 리뷰 FAIL (§21.7 R2).
> `신규` = 이 설계에서 새로 생기는 표면, `변경` = 기존 표면 수정, `기존` = 무변경 (인벤토리에만 등재).

## 3. 결제 실패 화면 (`payment_result_page.dart` `_FailBody`)

### 3.0 입력 계약 (developer 에게)

`PaymentResultPage(variant: fail)` 의 입력을 문자열 두 개 (`errorCode`, `errorMessage`) 에서 **의미 있는 한 개의 값** 으로 바꾼다.

```
PaymentFailure
  family   : launch (갈래 A) | gate (갈래 B) | unknown (갈래 C)
  reason   : enum — 알려진 6개 + unknown   (family == gate 일 때만 의미)
  menuItemIds : List<String>               (MENU_* 사유일 때 서버 토큰에서 파싱)
  launchCode  : String?                    (family == launch 일 때 Toss errorCode)
  rawCode     : String?                    (문의 코드 캡션용. 형식 검증을 통과한 토큰만. 원문 아님)
```

- 변환 함수는 **순수 Dart 하나** (`PaymentFailure.from(Object error)`) 로 두고 단위 테스트한다. 페이지 위젯은 `PaymentFailure` 만 받는다. `e.toString()` 을 페이지로 넘기는 호출을 `checkout_page.dart:137`·`:146` 에서 모두 없앤다.
- `family` 판별: `launchResult.success == false` → `launch`. `verifyAndCreateOrder` 예외에서 `[REASON]` 토큰을 읽어 **알려진 6개** → `gate`, 그 외 → `unknown`.
- 메뉴 id → 이름 변환은 페이지가 `cartProvider` 의 마지막 값 (`checkout_page` 가 `clearCart` 를 성공 경로에서만 부르므로 실패 시 카트가 남아 있다) 으로 한다. 페이지는 Firestore 를 읽지 않는다.

**버튼 동작 정의**

| 버튼 | 동작 |
|---|---|
| `카트에서 확인하기` / `카트로 돌아가기` | `Navigator.pop()` — 결제 화면이 `pushReplacement` 로 체크아웃을 대체했으므로 카트로 돌아간다. **MENU_* 사유일 때는 pop 직전에** `paymentRejectedMenuIdsProvider` 에 id 를 기록한다 (D6) |
| `다른 매장 둘러보기` | 홈 탭으로. 카트는 유지. `popUntil(isFirst)` + `selectedTabIndexProvider` 는 홈 탭 값으로 (성공 화면이 Log 탭을 고르는 것과 같은 방식) |
| `카트 비우고 메뉴 보러가기` | `clearCartUseCase` 후 `popUntil(isFirst)`. 카트 비우기 **확인 다이얼로그를 거치지 않는다** — 버튼 라벨이 결과를 말하고, 매장이 사라진 상태에서 되살릴 카트가 없다 |
| `닫기` | `Navigator.pop()` (주 버튼과 같은 곳). 시각적으로 주 버튼과 구별되는 텍스트 버튼 |

기존의 세 번 반복 (`다시 시도` / `결제 수단 변경` / `닫기` 가 전부 `pop()`) 은 갈래 B·C 에서 쓰지 않는다. **거절된 결제에 "다시 시도" 라는 버튼을 달면 같은 거절을 반복시킨다.**

### 3.2 갈래 A — 결제창 단계 실패 (Toss errorCode)

기존 `_mapErrorCode` 의 코드별 문구는 **그대로 유지**한다. 바뀌는 것은 `default` 한 줄이다.

| 항목 | 현재 | 변경 |
|---|---|---|
| 기본 문구 | `'$message (코드: $code)'` / `message ?? '결제에 실패했어요'` — Toss 가 준 원문 노출 | **`결제를 완료하지 못했어요. 다른 결제수단으로 다시 시도해 주세요`** (상수). `message` 를 절대 보간하지 않는다 |
| 문의 코드 | 코드가 문구에 섞여 있음 | 코드가 `^[A-Z][A-Z0-9_]{2,39}$` 형식이면 본문 아래 `오류 코드: {CODE}` (12 / `textMuted`). Q2 에서 거부되면 이 줄을 뺀다 |

### 3.3 갈래 C — 알 수 없는 실패 ("주문 확인이 필요해요")

돈이 나갔는지 모르는 상태다. **요금이 안 나갔다고 말하지 않는다.**

- 아이콘: `Icons.help_outline_rounded` size 64, `AppColors.warning`.
- 헤드라인: **주문이 완료됐는지 확인이 필요해요**
- 본문 (15 / `textBody`): `결제를 확인하는 중에 문제가 생겼어요. 이미 결제가 처리됐을 수 있어요. Log 에서 주문이 보이는지 먼저 확인해 주세요.`
- 보조 본문 (13 / `textMuted`): `Log 에 주문이 없다면 잠시 후 다시 결제해 주세요. 요금이 청구됐는데 주문이 없으면 관리자에게 문의해 주세요.`

|---|---|

## 4. 카트·체크아웃·빠른 재주문 (선검증 UI)

### 4.0 선검증이 보내는 결과 (UI 가 소비하는 값)

`ValidateCheckoutUseCase` 의 결과는 UI 관점에서 이 셋 중 하나다.

| 결과 | UI 의미 |
|---|---|
| `violations` (1건 이상) | 위반을 **직접 읽어서 확인함** — 표시 가능 |
| `none` | 위반 없음 **또는** 확인 실패 (UI 는 구분하지 않는다. 구분할 수도 없어야 한다 — N1·N2) |

즉 UseCase 의 반환 타입에 `failed` 를 두지 않는다 (또는 두더라도 UI 가 `none` 과 같은 경로로 처리한다). **단 "다시 확인" 버튼 (N3) 은 예외**로 실패를 알아야 하므로 별도 파라미터 `reportFailure: true` 로 호출하고 실패 시 예외를 던진다.

### 4.1 카트 행 (`cart_line_tile.dart`)

입력 추가: `availability` — `CartLineAvailability { normal, soldOut, unavailable, rejectedByServer }` (N2: `verified` 없음).

| 상태 | 시각 | 행 하단 캡션 | 행 동작 |
|---|---|---|---|
| `normal` | **현재와 동일** | 없음 | 현재와 동일 |
| `soldOut` | 썸네일에 `SoldOutOverlay(fontSize: 11, padding: EdgeInsets.symmetric(horizontal: 10, vertical: 4))` (메뉴 카드와 같은 색 규칙). 이름·옵션·금액 텍스트 `Opacity 0.45` (메뉴 상세 `menu_item_detail_page.dart:126` 와 같은 값) | `지금은 품절이에요` 12 / w600 / `AppColors.error` | 수량 스테퍼 비활성 (`IgnorePointer`). **`빼기` 버튼 노출** |
| `unavailable` | 썸네일에 `SoldOutOverlay(showLabel: false)` (덮개만 — 글자 `품절` 은 사실이 아니므로 쓰지 않는다). 텍스트 `Opacity 0.45` | `이 매장에서 더 이상 판매하지 않아요` 12 / w600 / `AppColors.error` | 스테퍼 비활성, `빼기` 노출 |
| `rejectedByServer` | 오버레이 **없음**. 이름 옆 변화 없음 (클라이언트 읽기는 정상이므로 "품절" 이라고 단정하지 않는다) | `직전 결제에서 확인된 메뉴예요. 지금은 바뀌었을 수 있어요` 12 / w500 / `AppColors.warning` | 스테퍼 **활성** (막지 않는다, N6). `빼기` 노출 |

`빼기` 버튼:
- 위치: 캡션 오른쪽 끝 (`Row` 의 `Spacer` 뒤).
- 스타일: `TextButton`, 라벨 `빼기` 13 / w700 / `AppColors.error`, 터치 영역 **최소 44 x 44** (`minimumSize`, `tapTargetSize: padded`).
- 동작: 기존 `onRemove` (`removeCartItemUseCase`) 와 **같은 호출**. 확인 다이얼로그 없음 (이미 못 사는 메뉴를 빼는 것이므로).
- 우상단 `X` 아이콘 (기존 `라인 삭제`) 은 그대로 둔다. `빼기` 는 위반 행에서 **의도를 말로 보여 주는** 보강이다.

캡션 줄은 위반 행에서만 추가되므로 **그 순간 행 높이가 늘어난다.** 선검증 결과가 늦게 도착해 레이아웃이 한 번 움직인다. 이를 `AnimatedSize(duration: 200ms, curve: easeOut)` 로 완화한다. 스켈레톤·로딩 표시는 두지 않는다 (N1: 로딩 중 "확인 중" 표시를 하면 통과 후 사라지는 것이 곧 "확인됨" 신호가 된다).

### 4.2 카트 상단 배너 (신규 `CartAvailabilityBanner`)

위치: 카트 목록 맨 위, 매장 카드 위. `Padding(fromLTRB(20, 12, 20, 0))`. 표시 조건: 위반 1건 이상 (`soldOut` / `unavailable` / `rejectedByServer` / 매장 불가).

```
Container
  padding: 14 (가로 16)
  background: AppColors.warning alpha 0.08
  border: AppColors.warning alpha 0.35 / 1px
  borderRadius: 16
Column
  Row: Icon(Icons.error_outline_rounded, 18, AppColors.warning) + 8 + 제목 (14 / w700 / AppColors.textHeading)
  SizedBox(6)
  본문 (13 / w400 / AppColors.textBody / height 1.5)
  SizedBox(10)
  Row(mainAxisAlignment: end): TextButton `다시 확인`
```

| 변형 | 제목 | 본문 |
|---|---|---|
| 품절·판매중단 (`soldOut` / `unavailable` 가 1건 이상) | `결제하려면 확인이 필요한 메뉴가 있어요` | `표시된 메뉴를 빼고 결제해 주세요. 방금 다시 판매를 시작했을 수도 있으니 `다시 확인`을 눌러 보세요.` |
| 서버 지목만 있는 경우 (`rejectedByServer` 만) | `직전 결제에서 문제가 있던 메뉴가 있어요` | `표시된 메뉴를 빼거나, 상황이 바뀌었을 수 있으니 `다시 확인`을 눌러 보세요.` |
| 매장 불가 | `지금은 이 매장에서 주문할 수 없어요` | `잠시 후 `다시 확인`을 눌러 보거나, 다른 매장에서 담아 주세요.` |

- 본문에 메뉴 이름을 **넣지 않는다.** 이름은 해당 행이 지목한다 (이름이 두 곳에서 갈라지지 않게). 
- `다시 확인` 버튼: 라벨 13 / w700 / `AppColors.primaryBright`, 터치 영역 44.
  - 탭 → 버튼 자리에 `SizedBox(16x16) CircularProgressIndicator(strokeWidth 2, AppColors.primary)`. 신선 읽기.
  - 결과 위반 있음 → 배너·행 갱신 (변화 없음 가능).
  - 결과 위반 없음 → **배너가 `AnimatedSize` 로 사라지고 `paymentRejectedMenuIdsProvider` 를 비운다.** 어떤 "문제 없음" 메시지도 띄우지 않는다 (N1).
  - **읽기 실패 → 하단 `SnackBar`: `확인하지 못했어요. 잠시 후 다시 눌러 주세요`** (2초). 배너는 그대로 (N3).
- 배너는 카트 화면에 들어올 때·앱이 포그라운드로 복귀할 때 **자동 선검증 결과**로 나타난다. 자동 선검증의 실패는 배너 없음 (N3).

### 4.3 카트 하단 바 (`_CheckoutBar`)

| 항목 | 변경 |
|---|---|
| 합계 줄 | 위반 행이 있으면 합계 줄 아래 `품절·판매중단 메뉴 N개가 포함된 금액이에요` 11 / `AppColors.textMuted` 한 줄 추가. 금액 자체는 바꾸지 않는다 (CartEntity 무변경) |
| `결제하기` 버튼 | **항상 활성** (N6). 스타일 변경 없음 |
| `결제하기` 탭 (이미 `authUser` 확인 후) | ① 버튼에 `_processing` 스피너 (기존 체크아웃 버튼과 같은 20x20 `onPrimary`) ② 신선 선검증 (타임아웃 3초) ③ **위반 없음 또는 확인 실패 → 기존대로 `CheckoutPage` push** ④ **위반 있음 → push 하지 않는다.** 카트 행·배너를 갱신하고 **첫 위반 행으로 스크롤** (`Scrollable.ensureVisible`, 250ms). 토스트·다이얼로그 없음 (사용자는 이미 카트 화면에 있다) |

spec §7.4 는 "체크아웃 진입 시 1회 + 결제 버튼 직후 1회" 이다. 체크아웃 진입은 **카트의 이 탭 1곳뿐** (`cart_page.dart:312` 만 `CheckoutPage` 를 push 한다) 이므로 진입 시 검증을 별도로 두지 않고 **이 탭이 진입 검증**이다. 2회째는 §4.4.

### 4.4 체크아웃 결제 탭 가로채기 (`checkout_page.dart`)

탭 → `_processing = true` → 신선 선검증 (타임아웃 3초) → 통과/확인 실패면 기존 `launchPayment`. 위반이면 **시트** (`showModalBottomSheet`, `isDismissible: true`, `useSafeArea: true`).

```
Container (BottomSheet)
  background: AppColors.surfaceElevated
  top radius: 20
  padding: fromLTRB(20, 12, 20, 16 + bottomInset)
Column(min)
  핸들: 36 x 4, AppColors.border, radius 2, 가운데
  SizedBox(16)
  제목 (18 / w700 / AppColors.textHeading)
  SizedBox(8)
  본문 (14 / w400 / AppColors.textBody / height 1.5)
  SizedBox(12)
  목록 카드 (§3.5 와 같은 컴포넌트 재사용, 헤더 `빼야 하는 메뉴`)
  SizedBox(16)
  주 버튼 (높이 52 / 반경 12 / AppColors.primary + onPrimary) `이 메뉴 빼기`
  SizedBox(8)
  라인 버튼 (높이 52 / AppColors.surfaceElevated + AppColors.border + textBody) `카트에서 확인하기`
```

| 위반 종류 | 제목 | 본문 | 주 버튼 |
|---|---|---|---|
| 메뉴 (품절/중단/없음) | `결제하기 전에 확인이 필요해요` | `아래 메뉴는 지금 주문할 수 없어요. 빼고 계속하거나 카트에서 확인해 주세요. 결제는 아직 시작되지 않았어요.` | `이 메뉴 빼기` (여러 개면 `이 메뉴 모두 빼기`) |
| 매장 | `지금은 이 매장에서 주문할 수 없어요` | `잠시 후 다시 시도하거나 다른 매장에서 주문해 주세요. 결제는 아직 시작되지 않았어요.` | `카트로 돌아가기` (목록 카드·보조 버튼 없음) |

동작:
- `이 메뉴 빼기`: 위반 행을 `removeCartItem` 으로 제거 → 시트 닫기 → **체크아웃에 머문다.** 합계가 바뀌었으므로 **자동 결제하지 않는다.** 합계·결제 버튼 라벨이 갱신된 것을 고객이 보고 다시 탭한다. 카트가 비면 기존 `_EmptyCart` 가 나온다.
- `카트에서 확인하기`: 시트 닫기 → 체크아웃 `pop` → 카트가 위반을 표시한 상태.
- 시트 바깥 탭/아래로 스와이프: 시트만 닫는다. 결제는 시작되지 않는다. `_processing` 해제.
- **시트는 취소 가능하다 — 결제를 시작하는 단계가 아니다.** 시트에서 "그래도 결제" 버튼은 **없다** (위반은 서버가 어차피 거절한다).

### 4.5 빠른 재주문 (`quick_reorder_section.dart`)

현재 순서: 카트 교체 확인 → **카트 비우기** → 투입 → `CartPage`. 투입 전 검증을 끼우되 **카트 비우기보다 앞**에 둔다 (모두 위반인 경우 기존 카트를 날리지 않도록).

순서: ① (다른 매장 카트면) 기존 `showReplaceCartDialog` ② **신선 선검증** (candidate 의 items + 매장) ③ 결과에 따라:

| 결과 | 동작 |
|---|---|
| 위반 없음 / 확인 실패 | 기존대로 비우기 → 투입 → `CartPage` (확인 실패는 서버 게이트에 맡긴다) |
| 매장 불가 | 다이얼로그 `지금은 이 매장에서 주문할 수 없어요` / 본문 `잠시 후 다시 시도해 주세요.` / 버튼 `확인`. **카트를 건드리지 않는다** |
| 일부 위반 | 다이얼로그 (아래) |
| 전부 위반 | 다이얼로그 제목 `지금은 주문할 수 있는 메뉴가 없어요` / 본문에 이름 목록 + `모두 품절이거나 판매가 중단됐어요.` / 버튼 `확인`. **카트를 건드리지 않는다** |

일부 위반 다이얼로그 (`AlertDialog` — `cart_page.dart` 의 `_confirmClear` 와 같은 스타일: `surfaceElevated`, 반경 16):
- 제목 `일부 메뉴는 지금 담을 수 없어요` (16 / w700 / `textHeading`)
- 본문: 이름 목록 (줄마다 `• {이름}` 13 / w500 / `textBody`, 전부 열거) + 빈 줄 + `나머지 메뉴만 담을까요?` 
- 버튼: `취소` (`textMuted`) / `나머지 담기` (`primary`, w700)
- `나머지 담기`: 카트 비우기 → **위반이 아닌 품목만** 투입 → `CartPage`. 카트 화면에는 빠진 메뉴의 표시가 없다 (이미 다이얼로그에서 말했다).
- `취소`: 아무것도 변경하지 않음 (기존 카트 유지).
- 토스트로 처리하지 않는 이유: 스낵바는 2초 뒤 사라지고 **이름이 복구 수단**이다. 사용자가 읽고 선택해야 하는 정보이므로 다이얼로그.
- 메뉴 이름은 `candidate.sourceLog.items[].menuItemName` (과거 주문 스냅샷). 이 이름이 현재 메뉴 이름과 다를 수 있으나 고객이 시켰던 이름이므로 알아본다.
- 단가 역산 (`_unitPriceFromLineTotal`) 제거는 이번 범위 밖 (N5).
- 로딩: 기존 `_busy` (카드 전체 `IgnorePointer` + 기존 진행 표시) 재사용. 별도 UI 없음.

## 5. brand 정보 화면 brandKey 행 (`brand_info_page.dart` `_BrandKeyRow`)

### 5.0 전제

`brandKey` 는 이제 부모 `BrandEntity` 에 없고 `brands/{id}/private/profile` 에서 별도로 읽는다 (**별도 비동기**). 현재 코드의 버그 구조 — `brand.brandKey.isNotEmpty` 를 "발급됨" 으로, `isEmpty` 를 곧바로 "승인 후 발급" 으로 읽는다 (`brand_info_page.dart:190`, `:260`) — 는 **읽기 실패와 미발급을 같은 문구로 만든다.** 새 구조에서는 이를 비동기 3상태 (`loading` / `data` / `error`) + `data(null)` 로 분리한다.

이 화면에는 brandKey **발급 버튼이 없다** (발급은 admin 승인 CF). 이번 설계도 만들지 않는다. 혼동의 위험은 **문구**이지 버튼이 아니다.

### 5.1 상태 정의

행 단독 상태다. **이 행이 실패해도 화면 나머지 (이름·상태·적립률) 는 정상으로 그린다** (전체 에러 화면으로 번지지 않게).

| # | 상태 | 조건 | 아이콘 / 색 | 제목 | 보조 문구 | 가능한 동작 |
|---|---|---|---|---|---|---|
| S0 | **로딩** | private 읽기 진행 중 (재시도 직후 포함) | 없음 | 라벨 `브랜드 키` (12 / `textMuted`) 아래 **스켈레톤 막대** 높이 16 / 너비 160 / 반경 4, 색 `AppColors.surface` (shimmer highlight `AppColors.surfaceElevated`) | 없음 | 없음 |
| S1 | **발급됨 (읽기 성공 + 키 있음)** | 읽기 성공 && `brandKey` 비어 있지 않음 | — | 기존 레이아웃 그대로 (키 값 monospace + 복사 아이콘) | 기존 `이 키를 점주에게 공유하면 가맹점 등록 시 사용할 수 있어요` | **복사** |

### 5.2 위치·레이아웃

- 기존 위치 유지: 상태 카드 안, 구분선 아래, `rejected` 제외 (기존 조건 `brand.status != EntityApprovalStatus.rejected` 유지).
- `S3` 는 `Row(Icon, 8, Expanded(Column(제목, 4, 보조)), 8, 다시 시도)`. 좁으면 `다시 시도` 가 다음 줄로 내려오지 않게 `Flexible` 로 문구를 줄이고 버튼은 고정 폭.
- S1~S4 전환 시 높이가 달라지므로 `AnimatedSize(200ms)`.

### 5.3 pending 이면서 키가 이미 있는 경우 → Q4

브랜드가 승인 후 정보를 수정하면 `pending` 으로 회귀하고 키는 보존된다 (`brand_repository_impl.dart:110`). 현재 UI 는 이때 `관리자 승인 후 브랜드 키가 발급됩니다` 를 보여 주는데 **이미 발급된 키가 있으므로 사실이 아니다.** 새 구조는 키 존재 여부를 읽어서 알 수 있다. 선택지는 Q4.

### 5.4 점주 매장 등록 폼 brandKey 조회 (`store_core_form_page.dart`)

현재: 조회 결과 `null` → `showErrorDialog('정상 브랜드 키가 아닙니다. 다시 확인해주세요')`. 예외는 바깥 catch 로 빠진다. CF 도입 후 **세 경우를 분리**한다. 표시 위치는 다이얼로그가 아니라 **필드 아래 인라인 에러** (`_BrandKeyField.errorText`, 이미 존재) — 오류가 일어난 곳에서 고칠 수 있게.

| 결과 | 인라인 문구 (12 / `AppColors.error`) | 이유 |
|---|---|---|
| 미매칭 (존재하지 않음 = 미승인, 동일 응답) | `브랜드를 찾을 수 없어요. 키를 다시 확인해 주세요. 키가 맞다면 브랜드가 승인 대기 중일 수 있어요` | 열거 오라클 방지를 위해 서버는 두 경우를 구분하지 않는다. 문구가 정적이므로 정보가 새지 않으면서 고객이 "맞는 키인데 안 된다" 에서 빠져나올 길이 생긴다 |
| 네트워크·서버 실패 | `확인하지 못했어요. 잠시 후 다시 시도해 주세요` | **미매칭과 다른 문구.** 키가 틀렸다고 오해시키지 않는다 |
| rate limit (`resource-exhausted`) | `조회를 너무 많이 시도했어요. 잠시 후 다시 시도해 주세요` | spec §15 |

- 복구 동작: 기존 제출 버튼 재탭 (`_submitting` 해제). 별도 `다시 시도` 버튼은 두지 않는다.
- 필드를 수정하면 에러 해제 (기존 `onChanged` 동작 유지).

## 6. 점주 매장 삭제 버튼 제거 후 그 자리 (`my_store_page.dart` `_DangerZone`)

### 6.1 결정: **안내 문구 한 줄을 둔다. 버튼·링크는 두지 않는다.**

세 안 비교:

| 안 | 대가 |
|---|---|
| 아무것도 안 둠 | 삭제 버튼이 있던 자리가 비어, 점주가 "어디 갔지?" 를 모른다. 폐업·잘못 등록·반려 후 정리를 하려는 점주에게 **다음 행동이 없다** (spec 의 U3: 버튼만 사라지면 "운영을 그만두려면" 을 물을 곳이 없어진다) |
| **안내 문구 (선택)** | 버튼 없음 = 오동작 경로 0. 문구가 올바른 곳 (임시 휴업 토글 / 관리자) 을 가리킨다. 비용: 점주가 읽어야 한다 |
| admin 문의 경로 (버튼/링크) | **앱 안에 문의 채널이 없다** (`grep 문의` → 전부 "관리자에게 문의해 주세요" 라는 **문구**일 뿐 링크·메일 없음, 환경 설정에 연락처도 없음). 연락처를 하드코딩하면 절대 규칙 4 (설정값 하드코딩 금지) 위반 위험이고, 없는 채널로 버튼을 달면 눌러도 아무 일도 안 일어난다 (U3 가 금지하는 상태). 채널이 생기면 이 행에 링크를 추가한다 → Q3 |

### 6.2 명세

기존 `_DangerZone` 위젯은 **삭제**하고 새 위젯 `_ClosingGuide` 로 교체한다 (호출 두 곳 `:317` `:391` 모두). 위치·간격은 기존 그대로 (`SizedBox(32)` 아래).

```
Padding(horizontal: 4)
  Row(crossAxisAlignment: start)
    Icon(Icons.info_outline_rounded, size: 14, AppColors.textMuted)   // 첫 줄 baseline 맞춤 위해 top padding 2
    SizedBox(8)
    Expanded(Text(문구, 12 / w400 / AppColors.textMuted / height 1.5))
```

- 컨테이너·테두리·배경 **없음** (카드로 만들면 "할 일" 처럼 보인다. 이것은 각주다).
- 빨강 (`AppColors.error`) **쓰지 않는다.** 위험 버튼이 사라지는 자리에 위험색이 남으면 눌러야 하는 것처럼 보인다.

문구 (매장 상태별):

| 대상 | 문구 |
|---|---|
| 개인 매장, `approved` | `잠시 쉬려면 '운영 정보 수정'에서 임시 휴업을 켤 수 있어요. 매장 운영을 그만두려면 관리자에게 문의해 주세요.` |
| 그 외 (`pending` / `rejected`) · 브랜드 가맹 매장 전체 | `매장을 삭제하거나 잘못 등록한 매장을 정리하려면 관리자에게 문의해 주세요.` |

- 임시 휴업 토글은 `store_operation_form_page.dart:114` 에 실제로 존재한다 (그 화면의 라벨과 문구를 맞춘다: `운영 정보 수정`).
- 임시 휴업이 주문을 실제로 막는지는 이 설계에서 확인하지 않았다. 문구는 "켤 수 있어요" 까지만 말한다. developer 는 `temporaryClosed` 가 결제 가능 여부에 영향을 주는지 확인하고 아니라면 첫 문장을 빼고 보고한다 (§8).

### 6.3 이미지 삭제 코드 제거

`_confirmDelete` 안의 Storage 이미지 삭제 (`:1000-1007`) 는 문서 삭제보다 **먼저** 이뤄져 실패 시 복구 불가 (spec §5-7). 이 코드는 `_DangerZone` 과 함께 사라진다. 이미지 정리는 admin `deleteStore` CF 가 한다.

### 6.4 spec 이 놓친 점 (Q3 로 제기)

가맹 매장이 **반려되면 점주는 재제출할 수 없다** (`_BrandRejectedBanner`: `재제출은 브랜드 본사에서 진행됩니다.`). 지금까지는 점주가 매장을 삭제하고 다른 키로 다시 등록할 수 있었다. 삭제가 막히면 **잘못된 브랜드 키로 등록한 점주가 스스로 빠져나올 길이 없다.** 관리자 문의로만 해결된다. 이번 범위(N4: 폐업 신청 흐름은 별도)로는 §6.2 의 두 번째 문구가 최선이며, 사용자가 이 공백을 인지하고 수용하는지 Q3 에서 확인한다.

| 삭제 중 | 화면 전체를 `IgnorePointer` + 하단 버튼에 스피너 + 상단 `LinearProgressIndicator(primary)`. 뒤로가기 차단 (`PopScope(canPop: false)`). 문구 `삭제하는 중이에요. 잠시만 기다려 주세요` (13 / `textMuted`, 버튼 위) |

| 삭제 실패 | 화면 유지, 입력값 보존. 버튼 위에 오류 박스 (`AppColors.error` alpha 0.06 배경 / alpha 0.3 border / 반경 12): `삭제가 중간에 멈췄어요` (14 / w700 / `error`) + `같은 매장을 다시 삭제하면 이어서 진행돼요. 삭제 이력은 중복 기록되지 않아요.` (12 / `textBody`) |
| 이미 삭제됨 (진입 후 문서가 사라짐) | 화면 대신 `이미 삭제된 매장이에요` + `목록으로` 버튼 |

- 실패 박스의 "이어서 진행" 과 "중복 기록되지 않아요" 는 spec §12 사실 4 의 `멱등: history 중복 방지 키` 에 근거한다. developer 가 이 성질을 구현하지 못하면 이 문구를 바꿔야 한다 (§9 전달 사항 4).
- 원시 예외 문자열은 이 화면에서도 노출하지 않는다 (D4).

## 8. 사용자 확인이 필요한 결정 (Q)

각 Q 는 선택지·대가·추천을 적는다. **직접 결정하지 않았다.** 추천안을 이 문서에 임시 반영해 두었으므로 사용자가 바꾸면 해당 절을 수정한다.

### Q1. 거절 화면의 "요금도 청구되지 않았어요" 를 문구로 쓸 것인가 (§3.4)

| 안 | 내용 | 대가 |
|---|---|---|
| **ⓐ 쓴다 (추천)** | `아직 결제되지 않았고, 요금도 청구되지 않았어요` | 고객의 첫 걱정 (돈이 나갔나) 에 즉시 답한다. 단 **사실이어야 한다.** Toss 승인 전 단계에서 카드사 "승인 문자" 나 일시 보류가 생기는지 실제 테스트 결제로 확인해야 한다 (T-2 항목 추가) |
| ⓑ 약화 | `아직 결제가 완료되지 않았어요` | 사실 오류 위험이 없다. 대신 고객은 "돈은?" 을 여전히 모른다 |
| ⓒ 돈 줄 없음 | 제거 | 가장 단순. 고객이 카드사에 전화하거나 재결제를 주저한다 |

추천 ⓐ (T-2 에서 사실 확인, 어긋나면 ⓑ 로 즉시 교체).

### Q2. 문의 코드 캡션 (`오류 코드: XXX`) 을 보여 줄 것인가 (§D4, §3.2, §3.3)

| 안 | 내용 | 대가 |
|---|---|---|
| **ⓐ 기본/갈래 C 화면에만 노출 (추천)** | 형식 검증을 통과한 토큰만 | 앱에 문의 채널이 없는 지금도 "코드를 알려 주세요" 한 줄이 현장 대응에 유용하다. 원문이 아니라 식별자이므로 `e.toString()` 문제와 다르다 |
| ⓑ 전혀 노출하지 않음 | 모든 화면에서 코드 비노출 | 원문 노출 위험 0. 대신 장애 보고 때 "무슨 화면이었는지" 만 남는다 |

### Q3. 점주가 "스스로 정리할 수 없는" 공백을 수용하는가 (§6)

삭제가 막히면 아래 점주는 관리자 문의 외에 길이 없고, **앱에 문의 채널 자체가 없다.**
- 폐업하려는 점주
- 잘못된 브랜드 키로 가맹 등록해 **반려된** 점주 (재제출은 본사만 가능)
- 중복 등록한 `pending` 점주

| 안 | 내용 | 대가 |
|---|---|---|
| **ⓐ 안내 문구만 (추천, 이 문서 반영)** | §6.2 | 범위 내. 공백은 N4 (폐업 신청 흐름) 에서 메운다 |
| ⓑ 안내 + 문의 채널 (메일/채팅 링크) 추가 | 링크 한 줄 | 채널과 연락처 설정값이 필요 (`--dart-define` 등). 채널 결정이 선행 |
| ⓒ 점주에게 "삭제 요청" 버튼 (요청 기록만 남김) | 신규 컬렉션·admin 큐 필요 | 사실상 N4 를 당겨 오는 것. 범위 2배 |

### Q4. 브랜드가 `pending` 으로 회귀했는데 키가 이미 있을 때 (§5.3)

| 안 | 내용 | 대가 |
|---|---|---|
| ⓐ 현행 유지 | 키를 숨기고 `관리자 승인 후 브랜드 키가 발급됩니다` | 문구가 사실이 아니다 (이미 발급됨). 담당자는 키가 사라졌다고 오해할 수 있다 — 이 설계가 막으려는 바로 그 오해 |
| **ⓑ 키를 보여 주고 주의 한 줄 (추천)** | 키 값 + 복사 가능 + `재승인이 끝나기 전에는 점주가 이 키로 등록할 수 없어요` (11 / `AppColors.warning`) | 상태를 정직하게 말한다. 키가 보여서 공유를 시도하는 담당자가 생길 수 있으나 주의 문구가 막는다. S1 의 변형 1개 추가 |
| ⓒ 키를 보여 주되 복사 비활성 | 복사 아이콘 흐리게 | 공유를 막지만 "왜?" 의 설명이 필요 |

### Q5. admin 삭제 진입점 (§7.0)

| 안 | 내용 | 대가 |
|---|---|---|
| **ⓐ 더보기 → `매장 관리` → 목록 → 삭제 화면 (추천)** | 신규 목록 화면 1개 + 삭제 화면 1개 | 승인 완료 매장 (폐업의 주 대상) 에 닿는다. 화면 2개 |

| ⓒ Console 유지 (UI 없음) | — | spec Q3 ⓑ 의 "이력이 남는 경로" 목적과 어긋난다 |

### Q6. 선검증 타임아웃 (D1·N4)

| 안 | 내용 | 대가 |

## 9. 개발자 / 설계자 전달 사항

### 9.1 설계자(architect) 확인이 필요한 것 (spec 에 없는 인터페이스)

1. **토큰 형식**: 이름 표시를 위해 CF 토큰에 `menuItemId` 가 필요하다. 제안: message 끝 `[MENU_SOLD_OUT:id1,id2]` (id 는 Firestore 자동 ID 라 `,` `:` 가 없다). 다른 사유는 `[STORE_NOT_SELLABLE]` 처럼 id 없음. spec §15 는 `[REASON]` 만 적었다. **id 가 없으면 §3.5 의 이름 목록은 항상 비어 이름 지목 요구사항이 충족되지 않는다.**
2. **admin 영향 범위 카운트 출처**: `deleteStore` 는 삭제 중에 `affected{}` 를 계산하지만 (spec §11.2) **삭제 전 확인 화면에는 그 숫자가 미리 필요하다.** 제안: `deleteStore` 에 `dryRun: true` (카운트만 반환, 쓰기 없음). 대안은 클라이언트 `count()` 쿼리 (admin Rules 로 서브컬렉션 읽기 가능 여부 확인 필요). 정하지 않으면 §7.2 가 구현되지 않는다.
3. **진행 중인 주문이 있는 매장의 삭제**: spec 에 가드가 없다. 삭제 화면 영향 범위에 `진행 중인 주문 N건` 을 넣을지, CF 가 거부할지 결정이 필요하다. 이 설계는 해당 행을 **넣지 않았다.**
4. **`deleteStore` 재실행 멱등**: §7.2 삭제 실패 문구는 "같은 매장을 다시 삭제하면 이어서 진행되고 이력이 중복되지 않는다" 에 의존한다 (spec §12 사실 4 의 `history 중복 방지 키`). 구현 방식이 달라지면 문구를 바꿔야 한다.

### 9.2 개발자

- **재사용**: `SoldOutOverlay` (`common/sold_out_overlay.dart`) — 카트 행 `soldOut` / `unavailable`; `ApprovalStatusBadge`, `BrandScopeBadge`, `StoreScopeBadge` — admin 목록; `_ErrorView` 구조 — admin 목록 에러; `AlertDialog` 스타일 (`cart_page.dart` `_confirmClear`) — 빠른 재주문 다이얼로그.
- **신규 위젯**: `CartAvailabilityBanner`, 체크아웃 차단 시트 (`CheckoutBlockedSheet`), 메뉴 목록 카드 (결제 실패 화면과 시트가 **같은 위젯**), `_ClosingGuide`, `AdminStoreListPage`, `AdminStoreDeletePage`, brandKey 행 4상태 위젯.
- **신규 순수 Dart**: `PaymentFailure.from(Object)` (§3.0). 페이지는 문자열 매핑을 하지 않는다.
- **삭제**: `payment_result_page.dart` 의 `_mapErrorCode` 에서 `'$message (코드: $code)'` / `message ?? ...` 폴백. `checkout_page.dart:137`·`:146` 의 `errorMessage: e.toString()`. `my_store_page.dart` 의 `_DangerZone` 과 `_confirmDelete`.
- **`paymentRejectedMenuIdsProvider`**: 메모리 전용 `Notifier<Set<String>>`. 소거 시점 — 카트 비우기, 해당 줄 삭제, 새 결제 시도 시작, `다시 확인` 에서 신선 읽기가 정상, 앱 재시작.
- **N2 가드**: `CartLineAvailability` 에 `verified`/`ok` 값을 추가하지 않는다. 코드 리뷰와 아래 가드 테스트로 고정한다.
- **카트 행 enum 이외의 "확인됨" 표시 금지**: 카트·체크아웃·빠른 재주문 어디에도 `Icons.check*` / 초록 (`AppColors.success`) 을 "재고·판매 가능" 의미로 쓰지 않는다.
- **자동 선검증 호출 시점**: 카트 화면 진입(`initState` 후 1회) · 앱 포그라운드 복귀 · `결제하기` 탭 · 체크아웃 `결제하기` 탭 · 빠른 재주문 탭. 카트 화면에서 스트림 변화마다 호출하지 않는다 (읽기 폭증).
- **가드 테스트 추가 제안** (spec §18.3 에 더해):
  - 모르는 토큰·임의 예외 문자열을 `PaymentFailure.from` 에 넣으면 **결과 어떤 텍스트에도 입력 문자열이 포함되지 않는다.**
  - 알려진 6개 사유 각각이 §3.1 표의 헤드라인·버튼을 가진다 (사유 추가 시 표 누락이 테스트 실패).
  - 갈래 C 화면에 `요금` / `청구` 단어가 없다 (돈을 단정하지 않는 규칙 고정).
  - `lib/presentation/customer/{cart,checkout}/**` 에서 `soldOut ==` / `status ==` 직접 비교 0건 (spec 가드 2 와 같은 범위).
- **`role_flows.md` 갱신**: §4.4 admin 표에 `매장 관리 (목록·삭제)` 행 추가, §4.2 owner 의 매장 삭제 행 제거.
- **`temporaryClosed` 확인**: §6.2 첫 문구는 임시 휴업이 실제로 주문을 막는다는 전제가 아니라 "켤 수 있다" 까지만 말한다. 그래도 `temporaryClosed` 가 고객 측에서 아무 효과가 없다면 첫 문장을 빼고 보고한다.

### 9.3 테스터

- T-2 추가: **거절 화면의 "요금 청구 없음" 사실 확인** (Q1) — 실제 테스트 카드/카카오페이로 게이트 거절을 일으키고 카드사 알림·결제 내역 확인.
- 자동 선검증 **네트워크 차단 상태에서** 카트 → 체크아웃 → Toss 창까지 진행되는지 (N3), 그리고 그 화면에 통과를 암시하는 요소가 없는지 (N1).
- 품절 거절 화면에 **메뉴 이름이 보이는지**, 2개 이상일 때 전부 보이는지, 같은 메뉴 옵션 2줄일 때 이름이 한 번만 나오는지.
- 서버가 지목했으나 카트 선검증은 정상인 경우 카트 행에 `rejectedByServer` 캡션이 보이는지.
- 빠른 재주문: 전부 위반일 때 **기존 카트가 유지되는지** (현행은 비우고 시작).
- brandKey 행 S0~S4 를 모두 유도 (읽기 차단으로 S3, 승인 후 키 삭제로 S4). **S3 에서 `관리자 승인 후 ...` 문구가 보이면 FAIL.**
- 점주 `my_store_page` 두 화면 (개인 / 가맹) 모두에서 삭제 버튼이 없는지.
