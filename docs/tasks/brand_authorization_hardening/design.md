# 1. 표면 인벤토리 — "브랜드 연결 상태" 사실 (R2)

| # | 표면 | ⓐ 판정 출처 | ⓑ **출처 읽기 실패 시 보이는 것** | ⓒ 복구 |
|---|---|---|---|---|
| 1 | 매장 승인 상세 — 브랜드 블록 | `brandByIdProvider(store.brandId)` 결과를 **4상태**(확인 중 / 승인됨 / 미승인 / 없음)와 **조회 실패**로 분류하는 단일 함수 `resolveStoreBrandLink` | `brands/{id}` 조회 실패 → **warning plate `브랜드를 확인하지 못했어요` + 승인 버튼 비활성** + `다시 시도`. 이름 폴백(`브랜드`) 금지 | `다시 시도` / 반려 |

| 4 | admin 허브 — 브랜드 링크 점검 카드 | `auditBrandLinks` 응답 | 호출 실패 → 카드 안 `점검하지 못했어요` + `다시 시도`. 실패를 "문제 없음" 으로 읽히게 두지 않는다 (§4) | `다시 시도` |

| 6 | 점주 `내 매장` 브랜드 매장 상세 (`my_store_page` `_BrandStoreDetailView`) | 같은 분류 (`BrandScopeBadge` 가 `storeBrandLinkProvider` 사용) | 헤더 이름은 브랜드 문서가 있을 때만 `{브랜드명} {지점명}`, 아니면 지점명만. 배지는 `브랜드 확인 중` / `브랜드 확인 필요`. **`브랜드 매장` 폴백 삭제** | 없음 (읽기 전용) |

| 8 | 브랜드 연결 실패 사유 (`BrandIdMissingView` 연결 실패 화면) | 서버가 싣는 사유 (`details.reason` / message `[reason]`): `already_linked` · `not_submitter` · `not_brand_account` · `brand_not_found` · 그 외 | 사유를 모르면 `retryable`(`다시 연결`) — 모르는 `failed-precondition` 을 "이미 연결" 로 단정하지 않는다. `not_brand_account` 는 별도 문구. `brand_not_found` 는 `다시 연결` 대신 `다시 확인`(재조회) | 사유별 (재시도 없음 3종 / 재조회 1종 / 재연결 1종) |

> 5~8 행은 3차 검증 F-3 / F-S2 로 추가했다 (개정 5). 이 표에 없는 표면을 "다른 표면이다" 라고 면제하지 않는다 — 면제가 필요하면 행으로 쓰고 ⓐⓑⓒ 를 채운다.

- 1·2 가 같은 분류 함수를 쓰는 이유: 같은 사실을 말하는 두 화면이 어긋나면(목록은 `브랜드`, 상세는 경고) 1차 H-3 와 같은 종류의 결함이다.
- 새 화면이 브랜드 연결을 말하게 되면 이 표에 행을 추가한다.

# 2. ⑤ 매장 승인 상세 — `AdminStoreApprovalDetailPage`

## 2-a. 왜 이 화면이 유일한 방어선인가

`brandKey` 는 비밀이 아니다 (`brands` read 가 `isSignedIn()` 전체 공개). 점주가 가짜 `brandId` 를 넣어도 Rules 가 가맹 관계를 증명할 수 없고, **실질 통제는 admin 승인뿐**이다. 따라서 이 화면은 admin 이 **무엇을 승인하는지**를 숨김 없이 보여줘야 한다. 현행은 반대다 — 브랜드가 없어도 `브랜드` 배지가 뜬다.

## 2-b. 상태 분류 `resolveStoreBrandLink(store, brandAsync)` (domain 순수 함수 + 표시용 provider 조합)

| 분류 | 조건 | 승인 버튼 |
|---|---|---|
| `personal` | `store.brandId` 가 null/빈 값 | 활성 (현행, 브랜드 블록 없음) |
| `checking` | 브랜드 조회 로딩 | **비활성** |
| `approved` | 브랜드 문서 존재 + `status == approved` | 활성 |
| `unapproved` | 존재 + `status` 가 pending/rejected | **비활성** |
| `missing` | 문서 없음 (조회는 성공) | **비활성** |
| `lookupFailed` | 조회 에러 | **비활성** |

- **승인 버튼은 `personal` 과 `approved` 에서만 활성**이다. 나머지는 모두 비활성 (fail-closed).
- **반려 버튼은 항상 활성**이다. 가짜 `brandId` 를 발견한 admin 이 그 자리에서 반려할 수 있어야 한다.
- 이미 승인/반려된 매장(처리 완료 상태)을 열었을 때도 같은 분류를 **정보로** 보인다(승인 버튼이 없으므로 비활성 개념 없음). 승인된 매장이 `missing`/`unapproved` 브랜드를 가리키면 admin 이 사후에 발견할 수 있게 같은 plate 를 그린다.

## 2-c. 화면 구성 변경

```
┌ AppBar  ‹  매장 승인 ───────────────┐
│ [대표 이미지 80] 매장 이름 22/w700     │
│              [승인 대기] [배지 ※2-d]    │  ← BrandScopeBadge 대체
│ (처리 완료 배너 — 기존)                 │
│ ┌ 브랜드 블록 (신규, 브랜드 매장일 때만) ┐│  ← 매장 정보 섹션 위
│ │ 소속 브랜드                            ││
│ │ …상태별 내용 (2-e)                     ││
│ └──────────────────────────────┘│
│ 매장 정보 / 영업시간 / 제출 메타 (기존)   │
├───────────────────────────────────┤
│ [승인 불가 사유 한 줄 — 비활성일 때]      │  ← 하단 바 위
│ [ 반려 ]            [ 승인 ]            │  ApprovalActionsBar
└───────────────────────────────────┘
```

- 브랜드 블록은 `store.brandId` 가 있는 매장에서만 그린다. **개인 매장은 현행 그대로**(블록 없음, 배지 `StoreScopeBadge.personal`).
- 블록은 `_SectionCard` 규격(기존 파일의 카드), 매장 정보 섹션 **바로 위**. 승인 결정에 가장 중요한 정보이므로 스크롤 없이 보이는 위치.

## 2-d. 상단 배지 (`BrandScopeBadge` 폴백 금지)

`BrandScopeBadge` 를 4상태로 고친다 (목록 · 상세 공용). `'브랜드'` 문자열 폴백은 **삭제**한다.

| 상태 | 배지 |
|---|---|
| 로딩 | `StoreScopeBadge` 기하 + 라벨 `브랜드 확인 중` (muted 틴트, 아이콘 없음) |
| 승인됨 | 현행 `브랜드: {이름}` |
| 미승인 | **`브랜드 미승인`** — `warning` alpha 0.18 + 아이콘 `Icons.warning_amber_rounded` 12 `warning`, 글자 `textBody` |
| 없음 / 조회 실패 | **`브랜드 확인 필요`** — 위와 같은 warning 규격 |

- 배지 글자는 `textBody` (§색상 규칙, 색 단독 전달 금지: 라벨 + 아이콘).
- 이름이 로딩 중이거나 실패했을 때 어떤 경우에도 `브랜드: 브랜드` 같은 자리표시 문자열을 만들지 않는다.

## 2-e. 브랜드 블록 내용 (상태별)

공통 헤더: `소속 브랜드` 12/w600 muted.

**① 승인됨 (`approved`)**

```
 소속 브랜드
 Q브루어리                                  17/w800 heading   [승인됨 배지]
 승인하면 이 매장은 이 브랜드의 가맹점이 돼요       12 muted
 ───────────────
 적립률    브랜드 5% 를 따라요                   ← 아래 상속 문장
```

**상속될 적립률 (승인하면 적용되는 값을 명시)** — 해석은 `resolveEffectiveRate` 를 **이 매장의 개별 값 없음(신규 매장)** 입력으로 한 번 돌린다. 문장은 한 함수가 만들어 승인 다이얼로그와 글자 그대로 공유한다.

| 해석 결과 | 문장 (13 body) | 보조 (12 muted) |
|---|---|---|
| 브랜드 적립률 유효 | `승인하면 브랜드 "{이름}" 의 적립률 {b}% 를 따라요` | `이 매장은 이 값으로 Qoin 을 적립해요` |
| 브랜드 값 없음 → 전역 | `승인하면 전역 기본값 {g}% 를 따라요` | `브랜드에 따로 정한 적립률이 없어요` |
| 브랜드 `사용 안 함` | `브랜드가 적립 사용 안 함이라 이 매장도 적립되지 않아요` | `브랜드의 ‘적립 사용’ 을 켜야 적립돼요` |
| 무효 | `적립률 설정에 문제가 있어 승인 후에도 적립되지 않을 수 있어요` | — |
| 전역 설정 로딩 | skeleton 바 160x14 | — |
| 전역/브랜드 적립률 읽기 실패 | `적립률을 확인하지 못했어요` + 텍스트 버튼 `다시 시도` | **승인 버튼은 막지 않는다** (게이트는 "브랜드가 실재·승인됐는가" 이고 적립률은 정보). 그러나 문장이 비어 있음을 숨기지 않는다 |

- 숫자 위계는 §1 의 규칙: 명시 값(브랜드 적립률)은 `textHeading` w800, 전역 상속은 `textMuted` w600.
- 이 줄은 정보이지 경고가 아니다 (`warning` 색 아님). 단 `사용 안 함`/무효 문장 앞에는 `Icons.info_outline_rounded` 16 `warning`.

## 2-f. 승인 버튼 비활성 표현

`ApprovalActionsBar` 에 `approveEnabled`(bool) 와 `approveDisabledReason`(String?) 파라미터를 추가한다 (developer).

- 비활성 시 `승인` 버튼: 1차 비활성 규격(`textMuted` 배경, `onPrimary` 글자). 로딩 인디케이터와 구분(저장 중 아님).
- 바 위에 사유 한 줄 (11 muted, 중앙, 바 위 8px):

| 분류 | 사유 한 줄 |
|---|---|
| `checking` | `브랜드를 확인하고 있어요` |
| `unapproved` | `승인되지 않은 브랜드라 승인할 수 없어요` |

# 3. ⑥ 브랜드 연결 복구 — `BrandScaffold` 의 `brandId` 없음 분기

## 3-a. 현행과의 차이 (spec 의 `_BrandIdMissingView` 는 지금 없다)

spec D1-2 는 `_BrandIdMissingView` 를 복구 경로로 지목하지만 해당 뷰는 sub-phase 6 에서 폐기됐고, 지금은 `brandId` 가 비면 **곧바로 `BrandInfoFormPage(brand: null)`**(등록 폼)로 간다(`brand_scaffold.dart` L37). 이 구조에서는 연결(claim)이 실패하면 사용자가 **같은 브랜드를 다시 등록**하게 되어 고아 브랜드가 쌓인다(spec D1-2 가 막으려는 사건 그 자체). 그래서 이 명세는 `brandId` 없음 분기를 **게이트 뷰 `_BrandLinkGate`**(이름은 `_BrandIdMissingView` 를 복원해도 무방)로 되살려, **폼으로 가기 전에 항상 기존 제출 브랜드를 먼저 확인**한다. 신규 화면이 아니라 `BrandScaffold` 내부 상태이다 (BottomNav 숨김, 기존 동작과 동일).

## 3-b. 상태 기계

```
brandId 없음
  └ 조회: brands where submittedBy == uid
       ├ 로딩 ───────────────▶ [확인 중]
       ├ 조회 실패 ──────────▶ [확인 실패]  (폼으로 가지 않는다)
       ├ 0건 ────────────────▶ BrandInfoFormPage(brand: null)  (현행 등록)
       ├ 1건 ────────────────▶ 자동 claimSubmittedBrand → [연결 중]
       │                         ├ 성공 → profile 스트림 갱신 → 정상 BottomNav (SnackBar 없음)
       │                         └ 실패 → [연결 실패] / [이미 다른 브랜드]
       └ 2건 이상 ───────────▶ 가장 이른 submittedAt 1건으로 자동 claim → [연결 중]
                                 ├ 성공 → 정상 진입 + SnackBar (3-d)
                                 └ 실패 → [연결 실패] (3-d 문구 변형)
```

- **자동 재호출은 진입(분기 평가)당 1회**다. 실패하면 사용자 조작 없이 반복하지 않는다 (무한 루프·서버 부하 방지). 재시도는 사용자 버튼.
- 조회 중·연결 중 전환에서 등록 폼이 한 프레임이라도 보이면 안 된다 (폼에서 저장 → 고아 누적). 게이트는 상태가 확정될 때까지 [확인 중] 을 유지한다.

- **사용자에게 보이는 것**: 연결에 성공해 정상 화면에 들어온 직후 SnackBar 1회 (6초, 닫기 가능):
  **`브랜드 "{이름}" 에 연결했어요. 같은 계정으로 등록된 브랜드가 더 있어서 관리자가 확인할 거예요`**
- 이름을 문구에 넣는 이유: 자동으로 고른 것이 사용자가 의도한 브랜드가 아닐 수 있다. 이름을 보여야 사용자가 이상을 알아챌 수 있다.
- 지속 배너는 두지 않는다 (사용자가 조치할 수 없고 admin 의 점검 카드(§4 `orphan_brand`)가 알린다).
- 연결 실패 시에는 `연결 실패` 화면의 본문 변형: `등록한 브랜드가 {n}개 있어요. 가장 먼저 등록한 "{이름}" 으로 연결을 시도했어요` (n≥2). 버튼 `다시 연결`.
- **긴장점(§6 에 보고)**: 자동으로 고른 브랜드가 의도와 다를 때 사용자 스스로 되돌릴 방법이 없다 (D4: 교정은 admin 전담). 화면은 이름을 노출하고 admin 문의를 안내하는 데까지만 한다.

# 4. ⑦ (임시) 브랜드 링크 점검 카드 — `AdminBrandLinkAuditCard`

> **이 UI 는 임시다. 정리 커밋(spec §8-A2)에서 파일째 삭제된다.** `TRANSITIONAL(brand_authorization_hardening §4)` 마커를 카드 파일과 허브 마운트 한 줄에 붙인다. Qoin 마이그레이션 카드(`AdminQoinMigrationCard`)와 **같은 패턴**이며 서로 참조하지 않는다.

## 4-a. 핵심 원칙 — 쓰기 0

- 카드에는 **자동 교정 버튼이 없다.** `점검하기`(조회)만 있다. `auditBrandLinks` 는 요청에 `dryRun` 도 없는 읽기 전용 함수다.
- `mismatch` 는 **공격 증거가 아니다** (admin 수동 발급 계정은 `submittedBy` 가 admin uid 이거나 부재). 화면 어디에서도 `의심`/`공격`/`사칭` 단어를 쓰지 않는다. 라벨은 중립 사실만.
- 교정은 Console 에서 사람이 한다 (spec §4.2). 카드는 **각 분류의 한 줄 안내**와 **ID 복사**만 제공한다.

## 4-b. 위치·규격

- admin 허브 최상단. 순서: `AdminQoinMigrationCard` → `AdminBrandLinkAuditCard` → partial 배너 → 전역 카드… (Qoin design §19-5).
- `surfaceElevated` + `border`, radius 16, padding 16, 다른 카드와 gap 20. 제목 15/w700 `textHeading`: **`브랜드 링크 점검`**. 우측 상단 알약 `임시`(높이 20, `textMuted` alpha 0.12, 11/w600/`textBody`).

  - `store_*`: 매장 ID·이름, 브랜드 ID
- **분류별 안내(조치) 한 줄** (11 muted, 목록 아래; spec §4.2 요약):

# 5. 개발자 전달 특이사항

1. **`BrandScopeBadge` 의 `'브랜드'` 폴백을 삭제**한다. 로딩/미승인/없음·실패 4상태 (`resolveStoreBrandLink` 단일 함수를 상세·목록 배지·승인 버튼이 공유). 가드 테스트로 `?? '브랜드'` 패턴 0건을 단언한다.
2. **승인 버튼 활성은 분류가 `personal`/`approved` 일 때만.** 반려는 항상 활성. `ApprovalActionsBar` 에 활성 여부·사유 파라미터 추가. 다이얼로그는 `approved` 에서만 도달 가능.
3. **상속 적립률 문장**은 `resolveEffectiveRate` 를 "매장 값 없음" 입력으로 돌린 결과 한 함수에서 만들고 블록·다이얼로그가 공유한다 (문장 각자 조립 금지). 적립률 읽기 실패는 승인을 막지 않는다 (§2-e).
4. **`_BrandIdMissingView` 가 코드에 없다.** `BrandScaffold` 의 `brandId` 없음 분기를 `brands where submittedBy == uid` 조회 → 3분기 게이트로 바꾼다. **조회가 끝나기 전·실패 시 `BrandInfoFormPage` 를 절대 그리지 않는다.** 자동 claim 은 진입당 1회.
5. 0건 → 등록 폼, 1건 → 자동 claim, 2건+ → 최소 `submittedAt` 자동 claim + SnackBar. `failed-precondition`(이미 다른 브랜드) / `permission-denied` 는 재시도 버튼이 없는 안내.
6. 점검 카드는 **한 파일 격리 + 허브 마운트 한 줄**, 쓰기 호출 코드 0. 분류 라벨 매핑은 그 파일 안에.
7. 신규 색 토큰 0개. `Color(0x…)` 0건.
